Every signed-in person now has a dashboard of their own that the server stores and serves. `GET /ui/dashboard` returns it (the default dashboard when nothing is stored) and `PUT /ui/dashboard` saves it; both are internal routes, held by the role `user` through the new permissions `core.ui-shell.dashboard.read` and `core.ui-shell.dashboard.write`, and neither takes a user id. The dashboard is one document in the user preference `core.ui-shell.dashboard`: no new table and no migration. What is stored is never trusted, so a tile whose module left the profile, a widget you may no longer see, a bad size or an overlap is repaired when the dashboard is read, and the stored document is only changed by your next save. Saving a dashboard also needs `core.settings.preference.write`, which the role `user` already holds. Widgets of the `dashboard` slot may now declare where and how big they are on a grid of twelve columns (`grid`), a name, a description, an icon and a configuration schema; `GET /ui/navigation` lists them, and a widget entry with an impossible grid or an unknown icon stops the server at start. `core.settings` gains `setUserPreference(actor, key, value)` in its public service. The grid itself is not on screen yet and the public v1 API is unchanged.
