# Authorization

Who may do what in Scorpion, in one place: which route needs which permission, which checks the service repeats, who may read and write
which fields of each object, which fields only a dedicated route may change, and which fields no response ever holds. It documents what the
code does and why. The decisions are in [ADR-0005](../adr/0005-deny-by-default-before-authz.md) (deny by default),
[ADR-0014](../adr/0014-authorisation-model-and-dependency-direction.md) (the model) and
[ADR-0015](../adr/0015-identity-on-authz.md) (identity on authz); the mechanics of a decision (roles, the cache, token scopes, resource
policies) are in the [core.authz README](../../modules/core-authz/README.md) and are not repeated here. Authentication is in
[authentication.md](authentication.md), sessions in [sessions.md](sessions.md). This page backs ASVS 5.0 requirements 8.1.1, 8.1.2 and
8.2.3 ([docs/security/asvs/v8-authorization.yaml](asvs/v8-authorization.yaml)).

## Who can call

| Caller        | Is                                                | What it can do                                                                                                                         |
| ------------- | ------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| Anonymous     | No credential                                     | Only the routes marked **public** below. Every other route answers 401.                                                                |
| Session user  | A person with a session cookie                    | What the permissions of their roles allow. Roles are resolved from the database by user id; the client's idea of its roles is ignored. |
| Token         | A personal access token (`Authorization: Bearer`) | Only a permission that its scopes name **and** its owner holds. Routes that need a person, not a program, refuse it (403).             |
| Administrator | The role `admin`                                  | Every permission a loaded module declares, by resolution.                                                                              |

The roles `user` and `reviewer` are data. `user` holds the self-service permissions that the core modules contribute (`me.read`,
`session.manage`, the profile, avatar, password, e-mail, link and token permissions of `core.identity`, the inbox permissions and
`core.notifications.preference.read`, `core.settings.preference.read` and `.write`, `core.settings.vocabulary.read` and `core.blob.upload`); `reviewer` holds nothing
from the core. The modules add theirs (the registry modules give `user` the two `v1.read` permissions of the public API, `kpi.framework` its reads and `kpi.ingestion` `v1.read`, `v1.write`, `measurement.read` and `measurement.ingest`; see "The public API (v1)"). An administrator can change what a role holds, so the matrix names permissions, not roles.

## The two checks

Every request is checked twice, and the second check is the one that knows the resource.

1. **The route.** Every route declares `permission`, or `public: true` with a reason, or it fails when the module registers it. The
   request pipeline checks the permission before the handler runs and answers 401 (nobody) or 403 (not allowed). Nothing reaches a handler
   unchecked (ADR-0005, defect 1).
2. **The service.** Each service method that acts for a caller calls `ctx.authz.require(actor, permission, resource?)` again, so a job, another
   module or a future route cannot skip it. For an action on one resource the service passes the resource and checks it against the rows:
   whose it is, what state it is in, who asked for it. A permission is global; ownership and state are not, and the service decides them.

How each kind of route relies on the checks:

| Kind of route                                                                                                                                                              | Route check                                                        | Service check                                                                                                                                                                                                                                                                                                                              |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Public (sign-in, registration, reset, first-run, branding, legal pages, files by hash)                                                                                     | none, with the reason in the route                                 | The service validates the input and rate limits apply (`strict` bucket); a file is served by its content hash.                                                                                                                                                                                                                             |
| Self-service (sessions, tokens, profile, avatar, password, inbox, preferences)                                                                                             | the self-service permission                                        | Permission again, **and the rows are the caller's by construction**: the SQL is scoped to `actor.userId`, and no route takes a user id for these. Another user's row cannot be named, so it is answered like an unknown one (404), except an inbox item (403, see below).                                                                  |
| Administration of other people (pending list, approve, reject, roles, end sessions, any token)                                                                             | the administrative permission                                      | Permission again, plus the built-in protections below (not your own request, not your own roles, not the last Admin).                                                                                                                                                                                                                      |
| Delegated (membership decisions, role changes and removals by the managers of one organisation, the member list, the edit of an organisation and its logo by its managers) | the plain `…organisation.read`, which every signed-in person holds | **The service is the authorization**: it calls `require(actor, <scoped permission>, { type: 'organisation', id, … })` and the resource policy `organisation.member` answers for managers and members ([ADR-0034](../adr/0034-scoped-permissions-at-the-route-and-delegation.md)). A plain User passes the route and is refused here (403). |
| Operation and configuration (settings, secrets, vocabularies, audit, outbox, deliveries, test mail, upload)                                                                | the module's permission                                            | Permission again; there is no resource below the permission.                                                                                                                                                                                                                                                                               |

**Delegated routes.** Eight routes of `registry.organisations` show a plain permission in the table above and are still not open to
everybody: `GET /organisations/{id}/members`, `GET /memberships`, `POST /memberships/{id}/decision`, `POST /memberships/{id}/role`,
`POST /memberships/{id}/remove` (sprint 3) and `PATCH /organisations/{id}`, `PUT /organisations/{id}/logo` and
`DELETE /organisations/{id}/logo` (sprint 4) name `registry.organisations.organisation.read`, which every signed-in person holds, and the
**service** refuses a caller who is neither an Admin nor, for that organisation, a manager (or, for the member list, a member). For the
edit routes the service asks what the request needs (`type`, `abbreviation` and `name` need `…organisation.manage`, the other fields the
scoped `…organisation.edit`) and what the caller holds on that organisation; a manager who names an identity field is refused whole. An
unknown organisation is a 404 before the 403 (an organisation is readable by every signed-in person, so that reveals nothing). The pipeline
cannot tell these routes from an ordinary read: the matrix of `defect-01.privilege-escalation.test.ts` has a row for each that expects 403
for a plain User (the sample of an edit route names a real organisation), which proves the service answer, and a delegated route without
its service check is a defect (ADR-0034). `POST /organisations` and `DELETE /organisations/{id}` keep `…organisation.manage` at the route.
The routes of asking, withdrawing and the own list name `…membership.request` (role `user`) and act on the caller's own row only;
`GET /memberships/summary` answers zeros for a plain User.

**Delegated routes of `registry.services`.** `PATCH /services/{id}`, `PUT /services/{id}/icon` and `DELETE /services/{id}/icon` name the plain
`registry.services.service.read` that every signed-in person holds, and the **service** is the authorization (ADR-0034, ADR-0036): it asks
the scoped `…service.edit` (and `…service.edit-identity` when the request names the slug or the provider) on that service, which the policy
`service.member` answers from the approved membership of the provider, read at every call. The icon method decides before `blob.put`, so a
denied caller leaves no file. `POST /services` names `…service.create` (every User) and the service requires an Admin or an approved member
of the chosen provider. `PUT /services/{id}/publication` names `…service.publish` (Admin and Reviewer) at the route. The matrix of
`defect-01.privilege-escalation.test.ts` has a row for each that expects 403 for a plain User (the samples name a real service), which
proves the service answer for the delegated ones. No route names a scoped permission (`…service.edit`, `…service.edit-identity`,
`…service.read-contact`). No route names a scoped permission (`…membership.decide`, `…manage-roles`,
`…remove`, `…view-members`, `…organisation.read-contact`, `…organisation.edit`): the pipeline checks a route's permission without a
resource, which would turn a manager away.

Public routes, and why each is open: sign-in, registration, password reset, address confirmation and the OIDC start and callback are how
anonymous people become signed-in ones, and carry the `strict` rate limit; `POST /bootstrap/first-admin` needs the first-run token that
only the console shows and only while nobody is Admin; `GET /bootstrap/status` answers one boolean (is an Admin still missing) so that the
start page of a fresh install can show the form for that token, and is `false` for good after the first Admin; `GET /auth/oidc/providers`
lists the id, the display name and the icon hash of each sign-in provider and nothing else (no issuer, no client id), which is what a
button needs; `GET /branding` and `GET /legal/{page}` are what the sign-in page shows; `GET /files/{hash}` serves logos, provider icons
and avatars to the sign-in page, and a file is named by the SHA-256 of its content.

**The anonymous reads of M7 (ADR-0036 part 2).** Four more public routes exist, all `GET`, all in the `default` rate-limit group, none
changing anything, and each says in its `publicReason` why it is open: `GET /public/services/{ref}` and `GET /public/services/{ref}/schema-org`
answer for a service that a Reviewer or an administrator made public (`ref` is an id, a slug or an old slug); `GET /public/organisations/{id}`
and `GET /public/organisations/{id}/schema-org` answer for an organisation that is the provider or a consortium of at least one **public**
service. For everything else (a private service, an unpublished one, an unknown id or slug, an organisation whose services are all private, an
id that is no UUID, and **every** address while `service.allowPublic` is off) the answer is the **same 404 with the same body as an unknown
id**, never a 403, so existence is not revealed; the flag is read in the same statement as the record. A 200 carries `Cache-Control: public,
max-age=60`: the cache lifetime is the only delay before an unpublish is seen by a shared cache, and the server itself keeps no copy, so the
next request after an unpublish is a 404. The records are **separate response schemas with pinned field names** (the field tables below);
`public-records.test.ts` walks them. The fifth new route, `GET /services/{id}/schema-org`, is for a signed-in reader (`…service.read`), any
service, `Cache-Control: private, no-cache`, never the contact point or the stage.

The pages of the web app follow the same rule ([ADR-0027](../adr/0027-web-shell-catch-all-proxy-and-typed-client.md)): a page is public only
when its module says why and `PUBLIC_PAGES` of `core.ui-shell` lists it, and the server decides who may open a page from the same list that
builds the navigation. The sign-in, registration, recovery and first-admin pages are public; the profile needs
`core.identity.profile.read`. Public pages call only routes that are public or need the session the page checks for itself.

## The public API (v1)

Routes under `/api/v1` are the ones programs call ([ADR-0037](../adr/0037-public-api.md)). They follow the rules of every route, with these additions:

- **A v1 route is never public**, with one named exception: `GET /api/v1/openapi.json` (module `public-api`) describes the API (routes, schemas, the
  permission each route needs) and holds no record; it is also committed to the repository and drawn by the public page `/docs`. A walker
  (`public-api-full-profile.test.ts`) fails when any other v1 route is `public: true`, and when a v1 path appears that nobody listed.
- **A call needs a token.** `Authorization: Bearer` or `X-API-Key`; the token passes only for a permission that its scopes name **and** its owner holds
  (ADR-0015), checked at every call against the database. A session cookie is accepted on v1 as on any route (a person on the instance's own pages), and
  it never makes a response readable to another origin: `Access-Control-Allow-Credentials` is never sent.
- **CORS** is an allow-list of origins in the `public-api` setting `corsOrigins` (empty: same origin only). Only `/api/v1` answers a preflight, the
  header is the caller's own origin and never `*`, and `/api/internal` never carries a CORS header. The answer to a preflight names **the methods of the path asked about** (`GET, POST, OPTIONS` for `/api/v1/measurements`, `GET, OPTIONS` for the
  read-only paths), so a path never claims a method it does not have (`preflight.ts`, `preflight.test.ts`, `measurements.contract.test.ts`).
- **The first v1 write is `POST /api/v1/measurements`** (M10 sprint 2, [ADR-0041](../adr/0041-measurement-model.md)). A token needs the scope of the route,
  `kpi.ingestion.v1.write`, **and** the scope of the scoped permission the service checks for the token's owner, `kpi.ingestion.measurement.submit`; the owner must be
  an Admin or an approved member of the service's provider (ADR-0015: a token never does more than its owner). The scopes of `kpi.framework`'s reads are **not**
  needed: the service reads the KPIs and their bounds through trusted reads after its own scoped check. A session cookie on this route is refused without
  `X-CSRF-Token` (401, the check is in the authenticator for every method that is not safe, tagged `[ASVS-7.2.1]` in `measurements.contract.test.ts`); a token request
  with a stale cookie is a token request. A body is at most 500 items and 3 MiB (413 above), and the rate limit counts the request, not the items.
- **Every v1 call with `audit: true` is recorded** in the `api` channel of the audit trail, denied (401, 403) and limited (429) calls included, with the route
  template, the status and the id of the token (never the token). A call the rate limit turns away is recorded without the token id: the limit runs before the
  token is checked, so that a flood of guesses costs no hash each. The spec route is not audited.
- **A v1 read never returns what the module's internal read hides.** The v1 rows of the field tables are in "The v1 rows (token)" below, and `response-fields.test.ts`
  walks the v1 schemas: it pins the names of each v1 answer and fails on a contact field, an audit column or a hint for the screens. One permission per
  route family, `registry.organisations.v1.read`, `registry.services.v1.read`, `kpi.framework.v1.read` and `kpi.ingestion.v1.read`, held by the role `user` by default; a token needs the scope as well.

### The API reference (`/docs/reference`)

The reference is a document of the web shell, not a route of the API ([ADR-0038](../adr/0038-api-reference-with-scalar.md)), so it is not in the route table
above. It decides nothing:

- **It is public by design** (the landing page `/docs` is too): it holds no record, and the description it draws, `GET /api/v1/openapi.json`, is the one public v1
  route. A person who wants to call a route pastes a token into Scalar's authentication panel; the call goes from their browser to this origin, and the
  answer, 200, 401 or 403, is the server's (the pipeline and the service check the token and its scope as for any caller). The page never judges a token.
- **The token stays in the page.** `persistAuth` is off, so it is in no `localStorage`, `sessionStorage` or cookie; the proxy, the telemetry, the AI agent and the
  default fonts are off, and the policy of the document has `connect-src 'self'`, so a token cannot go to another host, even if a person types another
  server into the panel. The end-to-end journey (`apps/web/e2e/reference.spec.ts`) proves this under both base paths: the browser's storage and cookies
  are identical before and after a call, no request leaves the origin, and the secret is in no line of the audit trail and no line of the log.
- **The policy** of this one document differs from the instance's in `style-src 'unsafe-inline'` (Scalar writes styles while it runs), which is the only
  relaxation; scripts are `'self'` and a nonce, and the strict policy of every other page is tested to be unchanged. The document is the same for every
  request (it takes no input), so the relaxation has nothing to inject into.

## The rules that hold for everyone, Admin included

They are in the service, so no route has to remember them.

- **Nobody changes their own roles** (403), in `assignRole` and `removeRole` of `core.authz`. Tests: `authz.test.ts` ("refuses changing
  your own roles, even for Admin and in any letter case"), `roles.test.ts` ("refuses to change your own roles, Admin included, and keeps the
  last Admin"), `defect-01.privilege-escalation.test.ts` ("refuses Admin to change their own roles, and to approve or reject their own account").
- **Nobody approves or rejects their own request** (403). The account is the request: `approval.ts` passes `{ approval: true, requestedBy }`
  to `require`, and `core.authz` refuses when the requester is the caller, whatever roles they hold and whatever a resource policy says.
  Tests: `approval.test.ts` ("refuses to approve your own account", "refuses an approval on your own account whatever you hold, also with the
  permission in a custom role"), `defect-01` ("refuses an approver who holds the permission in a custom role to approve their own account").
- **Nobody decides on their own membership request, changes their own role or removes themselves** (403), a manager and an Admin included.
  The service passes `{ approval: true, requestedBy }` on every decision (the same built-in protection as for an account), refuses a
  role change whose target is the caller, and refuses a removal of the caller's own row ("use leave"). **A manager never removes
  another manager**: only an Admin does. Tests: `memberships.decisions.test.ts`, `defect-01.membership.test.ts` ("refuses an Admin and a
  manager their own request…", "refuses a manager to promote or demote themselves…", "refuses a manager and an Admin to remove
  themselves…").
- **Delegated rights are read at every call**: the policy asks the database, so a demotion or a removal takes effect at the next call
  (a decision that passed the check a moment before a demotion committed is allowed once, ADR-0034).
- **The last Admin cannot be removed** (409), also when two removals run at once (`authz.test.ts`). "Last" counts accounts that can sign in: a deactivated Admin does not count, and the last active Admin cannot be deactivated either (`roles.test.ts`, `user-admin.test.ts`).
- **A token is limited twice**: by its scopes and by what its owner holds (scope ∩ owner). A token with the broadest scopes cannot do what
  its owner cannot (`defect-01`, "answers 403 to a token on every admin route, whatever its scopes name, when its owner is a plain User").
- **Sensitive account changes need a recent authentication** (ADR-0025): changing the address, linking a provider, ending sessions
  (401 `reauthentication-required`).

## Fields, per object

There is **no field-level permission engine**, and none is needed for the objects that exist (M4b Decision 9). Field-level access is kept by
three plain rules, each enforced in code and tested:

1. **Reads have one shape per route.** A response is a fixed Zod schema listing the fields; the service builds it from named columns, never by
   returning a row. Two kinds of reader who may see different fields of one object (you and an administrator) use two different routes with two
   schemas. The walker `apps/server/src/response-fields.test.ts` fails when any response schema of the live registry, at any depth, names
   `secretHash`, `passwordHash`, `tokenHash`, `clientSecret`, `secret`, `password` or `token`. The only exceptions are the two responses that show a
   token's plaintext once, to its owner: `POST /tokens` and `POST /tokens/{id}/rotate`.
2. **Writes accept only the fields of their route.** Every request body is a strict Zod object: an unknown field (`status`, `roles`, `userId`) is a
   422, never ignored and never stored, so mass assignment is not possible. A field that only a dedicated route may change has no place in any
   other body.
3. **State decides what may change.** A rule that depends on the state of the object (a pending account, a revoked or expired token, a used link)
   is enforced in the service on the stored row, not in the client.

In the tables, **self** is the caller acting on their own object, **holder** is the holder of the permission named, and **Admin** is the role.
"Dedicated route" means the field changes only through that route and its permission.

**The upload and the form (M10 sprint 3).** `POST /kpi/ingestion/preview` and `POST /kpi/ingestion/runs` name the plain `kpi.ingestion.measurement.ingest` (held by the role `user`, a permission of

the run history and the import template (anonymous 401; a plain user, a Reviewer, a requested, rejected or left member and a member of another provider 403, tested for each entry point in

parsed rows, and a dry run and a commit both parse the same bytes again, so there is one trust path. The route's body limit is 2 MiB plus the multipart envelope (413 before the body is read); a file over 2 MiB inside it is a 422. An XLSX

function. The import template escapes every cell that starts with `=`, `+`, `-`, `@`, a tab or a carriage return. These upload controls are not in an ASVS chapter this repository claims (V5 is not assessed); they are tested and described in

### The RDF reads of the KPIs (token and anonymous)

`kpi.framework` (M9 sprint 4) writes its indicators and KPI sets as RIMO-shaped Turtle and JSON-LD, in two pairs of routes over **one model**
(`service/rdf-model.ts`). The model holds definitions only: indicators (name, description, example, qualitative, value type, bounds, thematic
category), their units, means of measurement and automation tools, and the KPI sets as categories. It has **no field** for a service, a person, a
token, a contact point or a measurement, so neither pair can say one; `kpi-rdf-routes.test.ts` fills a database with all of them and fails when a
marker of any appears in a body or a header of the four answers.

| Route                                                                   | Who reads it                                                         | Notes                                                                                                                                                                                                                                                                                                  |
| ----------------------------------------------------------------------- | -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `GET /api/v1/kpi/rimo.ttl` and `GET /api/v1/kpi/rimo.jsonld`            | `kpi.framework.v1.read` (a token whose scopes name it, or a session) | The family's one permission, held by the role `user`, checked in the pipeline and again in the service. Audited like the other v1 reads. `Cache-Control: private, no-cache`, `X-Content-Type-Options: nosniff`, no ETag. A query string is 422.                                                        |
| `GET /public/kpi/rimo.ttl` and `GET /public/kpi/rimo.jsonld` (internal) | anyone, with no token and no session                                 | **public**, with the reason in the route: the definitions are the shared vocabulary of the instance, meant for systems and people without an account. `Cache-Control: public, max-age=300` and a strong ETag; `If-None-Match` gets 304. **Why a token on the v1 pair.** The v1 pair is a read of the public API like `/categories` and `/indicators`: a program that holds a token reads the whole
family with one scope, and the call is in the audit trail with the token's id. **Why a public pair as well.** Decision 9 of the M9 plan: an IRI of an
indicator should lead somewhere a stranger can read what it means. The IRIs themselves still identify and do not dereference (the pair is a fixed address,
not the address of each IRI), and the public pair says only what the token-bearing pair says to every holder of the role `user`. What the instance
chooses to publish is therefore the **catalogue of indicators**, not anything about who runs which service; an operator who does not want it public
removes `kpi.framework` from the profile (there is no setting that switches the public pair off, see the backlog).

What the output is made of. No free text becomes an IRI: every IRI is built from a slug or a vocabulary key that a check constraint or the term key rule
restricts to `[A-Za-z0-9._-]`, joined to a validated base, and the writer refuses anything that is not a plain `http(s)` IRI before it writes it. Free text
(names, descriptions, examples, the name of a set) is written only as a literal, through one escaping function for Turtle and `JSON.stringify` for
JSON-LD (with `<`, `>`, `&` and the line separators escaped); both formats are rendered from one graph and the tests load each with a real parser
(`n3`, `jsonld`; dev dependencies, never in the server) to prove that a hostile name stays one literal and adds no statement.

## What the audit trail, events and logs hold

The same names are kept out of the three records, and each has its own test:

- **Audit trail:** the redaction above; `audit-routes.test.ts` ("stores a body and query only for the route that opted in, redacted at any
  depth" and the reset token, SMTP password and webhook secret cases).
- **Events:** a declared event holds ids, names and counts, never a credential (the token events carry the token's id and name, not its
  prefix or hash); the event schemas are strict (`decisions.test.ts` in `core.audit`), and `response-fields.test.ts` fails when a declared event names a secret.
- **Logs:** no password, hash, token or secret is logged; the existing tests of sprint 2 and `tokens-routes.test.ts` ("never contains a
  token, its secret, its hash or a password, through a whole life of one") read the logs of a full run.

## What this page does not claim

- **No per-role field projection.** An Admin sees the same fields of an object as anyone else with the permission; there are only the
  differences the tables name, and each is a separate route.
- **Resource policies** (access to one resource for a caller without the global permission) are in use since M6: the policy
  `organisation.member` of `registry.organisations` gives the managers and members of one organisation their rights on it (ADR-0034,
  tested through the real authoriser in `policy.test.ts`). The next one, `service.member`, arrives with M7, and this page gets its rows
  then. The route-level `scoped` flag that would let the pipeline pass such a caller is recorded and deferred in ADR-0034.
- **Contextual attributes** (time of day, address, device) are not used in any authorization decision. The only context is the recent
  authentication of a session, in [sessions.md](sessions.md).
- The routes of `registry.organisations` (M6) are in the table, and the field table of the organisation is above (the contact point, the
  logo and the two editor groups), and so is the one of the membership. The matrix is regenerated, and the walker and the response
  guard cover the routes of every registry module automatically.
