# M13 Sprint Plan: legacy data migration (`tools/migrate-legacy`)

Status: **draft, 2026-11-17. Nothing here is built.** The decisions in §13 are open and need the maintainer's answers before sprint 1 starts; the plan as a whole needs approval. It changes the scope of M13 in `implementation.md` (§12), because the legacy application in use is not the one the source documents describe (§0).

Scope source: [implementation.md](implementation.md) §5, M13, Gate 3 and the risk table; [architecture.md](architecture.md) A5 and "Migration from the current app"; [ADR-0039](adr/0039-gate-2-conditional-pass.md) (the open line of Gate 2); what M6 to M12 hand over (§2); and the source of the legacy application in use, **`ipk-bit/scorpion` at `5a92c31`** (2025-04-17, the tip of `main`; named by the maintainer on 2026-11-17).

M13 is size M in `implementation.md`: **three sprints (about three to four weeks for one developer)**. It adds **no module** and **no runtime dependency** of the server or the web app: the tool is a workspace package under `tools/` that boots the kernel with the `full` profile and calls the modules' services. It reads a **snapshot** of the legacy stores (files, §4), never a live legacy database. It releases as **`0.16.0`** (one ADR: ADR-0052). Gate 3 follows.

## 1. What the tool lets an operator do

1. **Take a snapshot** of the legacy instance with documented commands (Neo4j's HTTP Cypher endpoint, `influx query --raw`), into one directory. Nothing on the legacy side is changed.
2. **Write a mapping file** (JSON, checked by a Zod schema) for what the legacy data does not say: the value type, thematic category and unit of each KPI, the slug of each KPI set, stage spellings, the OIDC provider id, usernames that break the new rules. `migrate-legacy plan` writes a first version from the snapshot with every gap marked.
3. **Dry run**: `migrate-legacy run --dry-run` reads the snapshot and the mapping, transforms, validates every row against the new rules (the services' own validation; `upsertBatch` with `dryRun`) and writes a **report**: every legacy record, what it becomes, and every drop or change with its reason. Nothing is written to the new database.
4. **Run** against an empty or partly migrated instance. Re-running is safe: every record is found by its natural key (abbreviation, slug, `sub`, the measurement's unique key) and kept, updated or created; a second run over the same snapshot writes nothing new.
5. **Compare**: `migrate-legacy compare` reads every migrated measurement back through `kpi.ingestion` and checks it against the snapshot, service by service and month by month (Gate 3's three services by hand become a check of all of them).
6. **List** the holders of legacy API keys (name and address only, never a key) for the mail asking them to create a new token.

## 2. What earlier milestones hand to M13

- **Writes go through the services** (rule 5; `m6-sprint-plan.md:37`, `m7-sprint-plan.md:40`, `m10-sprint-plan.md:41`). There is **no system actor** (`packages/contracts/src/actor.ts:26`): the tool acts as accounts, as the demo seed does (ADR-0046): a migration administrator for most writes, and each migrated user for their own membership request (the state machine allows `request` by `self` only).
- **Identity:** `createUser(input)` (no actor; one auth method; `status: 'active'` for trusted callers); usernames `^[a-z0-9_-]{3,31}$`; `assignRoleAsSystem(tx, { userId, roleKey })` for the role of a migrated user (no permission, `assigned_by = null`). No method takes an id, a password hash or a timestamp, and none is needed (§3).
- **Organisations:** one table typed `provider` or `consortium` (ADR-0033), found by `findByAbbreviationAsSystem(type, abbreviation)`; abbreviations without white space or `/`, at most 64 characters; memberships `requested | approved | rejected | left`, at most 10 pending per user.
- **Services:** `create`, `update`, `setPublication`; required fields slug, name, stage, provider (`config/fields.ts`); the legacy `abbreviation` **is** the slug (ADR-0043); slug rule of ADR-0035; every service starts private (M7 decision 4); no delete.
- **KPI framework:** the mapping table of `modules/kpi-framework/README.md` ("Migration from the old application"): a category is a KPI set (ADR-0040), necessity is the set row's term; an indicator needs a `valueType` and a `thematic` term; the evaluation (headline KPI and aggregate) is set per KPI set.
- **Measurements:** `upsertBatch(actor, serviceId, rows, { source, dryRun })` is the only writer; at most 120 months and 25 000 rows per batch (ADR-0041: "M13 will chunk its history by ten years"); one row per indicator and month in a batch ("the last one wins" does not exist, so the tool deduplicates first); months after the current one and years before 1900 are refused; rows are checked against the service's effective KPI set **now**.
- **Vocabularies** keep the legacy spellings (`PROD`, `mandatory`, `sum`; ADR-0018), with `TERM` a proper stage.
- **Gate 2's open line** (ADR-0039): the staging run with real organisation and service data is cleared by this milestone's dry run, recorded in this plan.

## 4. Design

- **A workspace package** `tools/migrate-legacy` (`@scorpion/migrate-legacy`, private, not in an image), with a CLI `pnpm migrate-legacy <plan | run | compare | holders>`. It boots the kernel with the `full` profile against `DATABASE_URL` (migrations applied first, never by the tool) and gets the services from it, as `scorpion seed` does. Its commands are documented in its README (it is not a module, so it has no manifest).
- **Three stages:** _read_ (the snapshot into plain records, Zod-checked; no network), _transform_ (pure functions: legacy records plus the mapping into the operations and the report; table-driven tests), _load_ (the operations through the services, in dependency order: organisations, KPI framework, services, users and roles, memberships, measurements). `--dry-run` stops after the services' validation and writes nothing.
- **Snapshot, not a connection:** no Neo4j driver and no InfluxDB client in the repository. Neo4j 3.5 answers Cypher over HTTP (`/db/data/transaction/commit`, JSON); InfluxDB answers Flux with annotated CSV. The README gives the commands; the tool parses JSON and CSV. A snapshot has a manifest (the commands, the time, a SHA-256 of each file) that the report repeats.
- **The actor:** the tool creates (or finds) one account `legacy-migration` with the role `admin` the way `create-admin` does, and writes as it, so every write passes the same permission and validation as a request; it acts as a migrated user only for that user's membership request. The account is deactivated at the end of a run (`--keep-account` for a rehearsal).
- **Idempotent by natural keys:** abbreviation (organisations), slug (services, sets, indicators), OIDC subject (users), `(service, indicator, period)` (measurements, `upsertBatch`). A run records nothing of its own; the report of a second run says "kept" for everything.
- **The report** (JSON for the compare step and Markdown for people): counts per kind (read, created, kept, changed, dropped), then one line per dropped or changed record with the rule that decided it. It holds names and addresses (the mail list), so it is **sensitive**: written with mode 0600 and never committed. API key values never appear in it.
- **ADR-0052** records the snapshot, the actor and the idempotency.

## 6. Sprint 1: discovery, the snapshot and the registry

1. **Discovery** (first, on a real snapshot the maintainer takes, decision 2): the node labels, the properties per label (declared or not), the relationship types and counts, the InfluxDB measurement names, fields and time precision. Output: a short Markdown table in this plan (§14) that confirms or corrects §0 and §3; no data in it.
2. The package, the CLI, the snapshot reader (JSON and annotated CSV, Zod-checked), the snapshot manifest and its check.
3. The mapping schema and `migrate-legacy plan` (writes a mapping with every gap marked).
4. Transform and load for providers, consortia, services and their consortia; the report.
5. **Tests:** table-driven unit tests for each rule of §3 used here (slug, abbreviation, stage, licence, provider count, consortium links); integration tests against real Postgres (Testcontainers) with a **made-up snapshot** built by factories in `packages/testing` (no real names; rule 9): a dry run writes nothing (row counts before and after), a run creates what the report says, a second run creates nothing, a run stopped halfway and run again ends in the same state, a service the services refuse is reported and does not stop the others.

## 7. Sprint 2: KPIs, measurements, people

1. Indicators, KPI sets, service sets and additional KPIs.
2. Measurements: month-end, the "latest in the month" rule, the batches of 120 months, KPIs added as optional where a value would otherwise be refused; `upsertBatch` with `dryRun` in a dry run.
3. Users (OIDC identity, username rules), roles, memberships (request as the user, decision as the migration account), the migration account's life.
4. `migrate-legacy holders`: the list of key holders (name, address, number of keys).
5. **Tests:** the dedup and month-end rules as tables (a point on the 1st, on the 15th, two in one month, one under the old provider name, a future month, 1899); integration: ten years and one month of a service in two batches; a measurement of a KPI outside the set; a user whose username is taken; an address used twice; a membership approved and one pending; a key value never appears in the report, the log or the database (search all three); a denied case (the migration account without `admin` is refused at the first write, and nothing is written).

## 8. Sprint 3: compare, rehearsal, release

1. `migrate-legacy compare`: every migrated value against the snapshot, per service, KPI and month; differences listed with their reason (a dropped point is expected, an unexplained one fails).
2. **The rehearsal** on staging with a copy of production (the maintainer's, decision 2): snapshot, plan, dry run, run, compare, a second run (nothing new), the dashboard of three services checked by hand against the old app (Gate 3). The result goes into §14 with counts only.
3. The runbook in the tool's README: the snapshot commands, the order of the cutover (legacy read-only, final snapshot, run, compare, DNS switch), what to tell users (sign in with the same account; create a new token), how to repeat a run.
4. ADR-0052; `implementation.md` M13 and Gate 3 updated as approved (§12); changeset (`minor`: operators can migrate from the legacy application); release `0.16.0`.

## 9. How complete the migration is

**Complete** for what the legacy application in use stores, apart from the items below: every provider, consortium, service (with its provider, consortia, stage and licence), KPI set (from a category, with its KPIs and their necessity), indicator, service-specific KPI, measurement (one value per service, KPI and month), user (signing in with the same OIDC account), admin role and provider membership.

**Not migrated, by design:**

| What                                                                               | Why, and what replaces it                                                                                       |
| ---------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| API keys                                                                           | Stored in plain text in the legacy graph and unscoped; holders are mailed to create a scoped token (decision 5) |
| Passwords                                                                          | Not in the legacy data (Keycloak holds them); users sign in through OIDC as before (decision 3)                 |
| Points beyond one per month, future months, years before 1900                      | The new model keeps one value per month and these limits (ADR-0041); each is listed in the report               |
| Records the new rules refuse (a service with two providers, an address used twice) | Listed in the report; fixed in the legacy data or the mapping and the run repeated                              |
| The SQLite tables                                                                  | Vestigial, unless discovery shows otherwise (decision 10)                                                       |

**Not in the legacy data, so set up by hand after the run:** the headline KPI and aggregate of each KPI set (the impact page needs them; the legacy app computed them in the browser), the thematic category, unit and value type of each KPI (in the mapping file), descriptions, links, contact points and icons of services, the publication of services (decision 8), branding, legal texts and the instance's settings. Maturity, onboarding, publications and announcements have **no legacy data**: M14 to M17 start empty.

## 13. Decisions (open)

1. **Is `ipk-bit/scorpion` the only source?** Did the PostgreSQL application of `FEATURES.md` ever hold production data? _Recommended:_ the plan assumes not.
2. **Snapshots.** Who takes them, from where, and may sprint 1 have one for discovery (it stays on the maintainer's machine or staging; only counts and names of properties go into the plan)? _Recommended:_ the maintainer, one at the start of sprint 1 and one for the rehearsal.
3. **The OIDC issuer.** Which issuer gave the `sub` in `USER.id` (the Keycloak realm, or LS-AAI directly), and which provider will the new instance use? Users keep their accounts only if the issuer is the same. _Recommended:_ configure the same issuer in the new instance.
4. **Admin role.** The `admin` property of `USER`, or Keycloak's role mappings (what the legacy app checks)? _Recommended:_ Keycloak's, exported into the snapshot; the property as a cross-check in the report.
5. **API keys.** Not imported, holders mailed (the plan), or imported as tokens with the scopes of today's write? _Recommended:_ not imported: they were stored in plain text.
6. **`HAS_KPIS` without `DEFINES`.** Which necessity? _Recommended:_ `mandatory`, reported.
7. **Slugs that break the rule.** A new slug from the mapping; keep the legacy abbreviation anywhere? _Recommended:_ the mapping gives the slug; the report pairs old and new.
8. **Publication.** Every service private (M7's rule) or published as in the legacy catalogue? _Recommended:_ published, since the legacy catalogue showed every service; a mapping switch.
9. **A value for a KPI the service no longer has.** Add the KPI to the service as optional (the plan), or drop the value? _Recommended:_ add, so no value is lost.
10. **SQLite `users.db`.** Ignore it? _Recommended:_ ignore unless discovery finds rows newer than the Keycloak accounts.
11. **When to cut over.** The legacy application has no maturity, onboarding, bibliometrics or announcements, so nothing waits for M14 to M17. Cut over after Gate 3, or at Gate 4 as planned? _Recommended:_ after Gate 3.
