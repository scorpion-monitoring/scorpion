# M6 Sprint Plan: `registry.organisations`

Status: decided, 2026-10-09. The maintainer answered Decisions 1 to 13 (§15) and, in a follow-up the same day, the four points that those answers had created (Decisions 14 to 17, §13); the plan applies all of them. Two small points that the follow-up created are in §13, "Remaining questions" (each with a recommendation); the plan follows the recommendations until they are answered.
Scope source: [implementation.md](implementation.md) §4, M6, and the Gate 2 line that asks for a registry profile "added by M6, ADR-0030". Closes no defect of FEATURES §5; it builds on defect 1 (every route has a permission) and prepares defect 2 and 14 for M7 (the organisation side of the service ↔ consortium link). Releases as `0.8.0` (`0.7.0` is M5, released 2026-10-09, see [m5-sprint-plan.md](m5-sprint-plan.md)). Gate 2 follows M8.

M6 was size M (about 2 to 3 weeks for one developer) and grows to about **5 weeks** with the decisions of 2026-10-09: the organisation now serves a Schema.org profile with a logo, and membership is decided, plain members are removed and the descriptive fields of the organisation are edited by delegated organisation managers, which is the first resource-scoped authorization in the product. It is the first module that is **not** a `core.*` module: the first one that contributes to the registries of the core (`authz.resourcePolicy`, `authz.defaultRole`, `notify.template`, `ui.routes`, `ui.nav`, `ui.widget`), declares a registry of its own (`org.type`, `org.usage`), and is added to a profile that is not `core-only`. Everything it needs exists since M5; the risk is not new infrastructure but getting the first plugin's conventions right, because M7 to M17 copy them. This plan splits M6 into **five sprints** of about one week, each one `feature/m6-*` branch and one pull request into `dev`. M6 is released once, after sprint 5. The draft had three sprints and the first version of this plan four; §4 explains what moved.

## 2. Cross-sprint rules

- Stay inside M6. Anything else goes to `docs/backlog.md` (§11). Services, the service wizard, the catalogue and the public API are M7 and M8.
- **One pull request per sprint** (CLAUDE.md "Working style"). ADRs, READMEs, backlog lines, the generated route table and review fixes go into the sprint's pull request. Push and open it when the sprint is complete and verified locally: `pnpm check`, `pnpm test --filter @scorpion/registry-organisations` and the packages touched, the full `pnpm test` before the last sprint, `pnpm test:e2e` for the journeys that exist.
- **Module rules** (CLAUDE.md): one package `modules/registry-organisations` with `module.ts` and `public.ts`; dependencies only in `package.json` (`core.authz`, `core.settings`, `core.identity`, `core.notifications`, `core.blob` as dependencies; `core.ui-shell` as an optional peer, so the module starts in a profile without the shell); layers `ui/` → `routes` → `service/` → `db/`; tables carry the prefix `org_` (Decision 2); foreign keys point only to the module's own tables. **No foreign key to `identity_user` or to the blob table**: user ids and the logo's blob id are plain columns, as `core.authz` does, so a purge cannot be blocked.
- **No hard-coded lists.** Organisation types are a registry (`org.type`, Decision 3); the membership states and roles are the state machine of the service, a closed set of code with check constraints and no pg enum; limits (pending requests per person, managers per organisation, the `sameAs` count) are settings or named constants with a test; every label comes from the message catalogue or the type entry's labels per locale. A test fails on a pg enum.
- **No hard-coded branding** (CLAUDE.md rule 9): the JSON-LD and the mails take the instance origin, the instance name and the contact addresses from settings and the request, never from a constant. The organisation's contact address is the organisation's data, not the instance's.
- **Two editor groups on one record (Decision 14).** From sprint 4 the organisation record has two editor groups: Admin (every field, create, delete) and the managers of that organisation (the descriptive fields only). There is **one** `update` method and **one** logo path; the field-rules table (`service/field-rules.ts`, built in sprint 1 with Admin as the only group) says which access a set of fields needs, so the second group adds a policy answer and a route permission switch, never a second code path or a copy of the validation. A request that touches a field its caller may not write is refused **whole** (403), never partly applied.
- **Layer rule 5:** the service layer is the only way to change data. The routes, the purge subscriber and (later) the migration tool call the same methods. Every write that touches more than one row runs in `ctx.db.tx()` and emits its event and its mail inside it.
- **A service method needs:** an integration test against real Postgres (Testcontainers), a denied-permission case, a rollback case for a multi-row write (a mail that cannot be stored rolls the membership change back), and, for membership and removal, a concurrency case (two deciders at once; a removal racing a decision or a role change), and, for the organisation record, a case per editor group.
- **Pure logic gets table-driven unit tests:** the membership state machine (`transition(state, role, action, by)`), abbreviation and name normalisation, the type-entry check, the `sameAs` and ROR id validation, the JSON-LD builder and its escaping, the search escape (`%`, `_` and `\` in a query), the sort and page maths.
- **Routes** use `createRoute()` with a `permission`; every list uses the legacy envelope with 0-based pages and a stable sort (key, then id); invalid input is 422 and an unknown reference is 404 or 422, never 500; a new route gets an entry in the matrix of `apps/server/src/defect-01.privilege-escalation.test.ts`, a regenerated route table in `docs/security/authorization.md` (the test header says how), and `response-fields.test.ts` checks its schema by itself. There is no public route in M6 (§10); `public: true` is not used.
- **Security rules** (CLAUDE.md): check permissions twice (the route, and `ctx.authz.require(actor, permission, resource)` in the service for the resource-scoped ones); **nobody approves their own request and nobody changes their own role** (tests prove both); no secret, token or session id in a log or an event; a mail never carries more than the template needs; uploaded images go through the blob store (re-encode, sanitise SVG, size limits), never a data URL; no `{@html}` on unsanitised content (the one exception, the JSON-LD block, is decided in Decision 17, §13: one audited component).
- **Scoped paths.** M6 plans **no change** to `modules/core-identity/**`, `modules/core-authz/**`, `apps/server/src/pipeline/**` or `packages/contracts/src/route.ts` (Decisions 6, 8 and 14 keep it that way: the route carries a plain global permission, the service does the scoped check, and the policy of `core.authz` already receives the permission and the resource). **If the prototype of §0 item 8 or any later test shows that the delegation needs a change in a scoped path, the plan says so, stops, and the change comes with its V7 or V8 entries and tagged tests in the same pull request.** M6 does change **`docs/security/**`**, which maps to all four chapters (implementation.md §8.4): the regenerated `authorization.md`, the new field tables and the V8 evidence for resource-scoped authorization are such changes. Each sprint that regenerates it carries either the matching update of `v8-authorization.yaml` or the label `asvs-no-impact` with a description line that starts exactly `ASVS impact: none because <reason>`. Each sprint says which (sprints 1 and 2 the label, sprints 3 to 5 the YAML update).
- **A module with events** is added as an optional peer of `core.audit` (`package.json`, README of `core.audit`) and gets entries in `decisions.ts` in the same sprint; `decisions.test.ts` fails otherwise.
- Use the factories in `packages/testing`; add `makeOrganisation` (with optional logo, `sameAs`, ROR id and contact point) and `makeMembership` (with a `role`) there. Never hand-write fixture SQL.
- Update the module README in the same commit as every manifest change (permissions, settings, events, registries, routes). `core.notifications` and `core.audit` READMEs change where this plan says so.
- A test never calls a third party (no request to ror.org or to a `sameAs` URL: they are validated as strings only). No new runtime dependency is expected (Drizzle, Hono, Zod, the existing kernel, `core.blob` with its `sharp`, DOMPurify and ui-kit are enough); if one appears, the pull request description names it and says why.
- Every pull request carries a changeset (package `scorpion`), written for operators and API users: the new module, the new profile and image, the new permissions and routes, what an administrator and an organisation manager can now do. Sprints 1 to 4 are `minor` changesets; the release turns them into `0.8.0`.

## 3. Mapping of the organisation to schema.org

The organisation can serve a [Schema.org `Organization`](https://schema.org/Organization) profile (Decision 4). One pure function in the service, `toSchemaOrg(organisation, { origin, basePath, includeContact })`, builds it; the detail page, the API route and (M8) a public API route all use that function, never a second mapping.

| Stored field                    | schema.org property                                          | Notes                                                                                                                                             |
| ------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| `type` (the `org.type` entry)   | `@type`                                                      | the entry's `schemaType` (default `Organization`; an allow-list of schema.org subtypes of `Organization` in code, a test refuses another value)   |
| `id`                            | `@id`, `url` fallback                                        | the absolute URL of the detail page (instance origin and `BASE_PATH`, never hard-coded)                                                           |
| `name`                          | `name`                                                       |                                                                                                                                                   |
| `abbreviation`                  | `alternateName`                                              |                                                                                                                                                   |
| `description` (plain text)      | `description`                                                | plain text, never HTML                                                                                                                            |
| `website`                       | `url`                                                        | the organisation's own site (the `@id` identifies the record)                                                                                     |
| `ror_id`                        | `identifier`, and a `sameAs` entry                           | `identifier` is a `PropertyValue` (`propertyID: "ROR"`, `value: "https://ror.org/<id>"`); the same URL is added to `sameAs` once                  |
| `same_as` (list of URLs)        | `sameAs`                                                     | `http(s)` URLs only                                                                                                                               |
| `logo` (blob id and hash)       | `logo`                                                       | an `ImageObject` with `url` = instance origin + base path + `/api/internal/files/{hash}` (`GET /files/{hash}` is public, immutable and cacheable) |
| `contact_email`, `contact_type` | `contactPoint`                                               | a `ContactPoint` (`email`, `contactType`); present only when the reader may see it (Decision 4, sprint 2 item 6)                                  |
| (not stored)                    | `parentOrganization`, `subOrganization`, `address`, `member` | not built; hierarchy is out of scope (§11)                                                                                                        |

A property with no value is **omitted**, never `null` or an empty string. The same function feeds `application/ld+json` and the JSON-LD block of the page, so the two cannot differ. Who may write which stored field is the field-rules table of §5 item 7 and Decision 14 (§13).

## 5. Sprint 1: the module and the organisation record

**Branch:** `feature/m6-organisations-core`. **Goal:** an administrator can create, change, list and delete organisations of the two seeded types through the API, with their `sameAs` list, ROR id and contact point; another module can contribute a type and a reference check; the `registry` profile builds, starts and is published as an image.

Work items

1. **ADR-0032 and ADR-0033, and the lines of §12 in `implementation.md`** (first commit). ADR-0032 records the profile (Decision 1): name, module list now and in M7 and M8, why `full` keeps growing alongside it, and the CI and ghcr changes of item 9. ADR-0033 records the organisation model: one table typed by a registry entry (Decision 3), the fields and their schema.org mapping (Decision 4, §3), the `org.usage` registry (item 4), the contact point and its visibility (sprint 2, item 6), the logo through `core.blob` (sprint 2, item 4), the membership state machine, the role and its sprint 3 tables (Decisions 5 and 6), the two editor groups and the field rules per role (Decision 14; decided in sprint 1, finished in sprint 4), the table prefix (Decision 2), and why the abbreviation, not the name, is the lookup key. The sections on the profile, the logo and the contact point are written in sprint 1 as decisions and finished in sprint 2 when the code exists.
2. **Create `modules/registry-organisations`:** `module.ts` (a `defineModule` manifest, id `registry.organisations`, `tablePrefix: 'org_'`), `public.ts`, `README.md`, `package.json` (`@scorpion/registry-organisations`, exports `./module`, `./public`, `./ui`), `tsconfig.json`, `db/schema.ts`, `migrations/`, `routes.ts`, `service/`, `settings-schema.ts`. Run `pnpm modules:sync` so `defineProfile()` knows the id. Copy the shape of `modules/core-audit` (manifest closure around the service, `module.test.ts` that checks the manifest, README with the tables of permissions, routes, events, registries, settings).
3. **`org.type` registry** (declared by this module; Decision 3). An entry is `{ id, labels: { en, de? }, membership: boolean, schemaType?, order }`: `id` is a lower-case key (`provider`), `labels` are shown by the UI, `membership` says whether people may become members of an organisation of this type, `schemaType` names the schema.org class of the profile (default `Organization`, §3). The module contributes `provider` and `consortium` itself (both `membership: true`, as FEATURES §3.4 and M6's "consortium membership too" ask). A second module can add `funder` (`membership: false`, `schemaType: 'FundingAgency'` if the allow-list has it) without editing this one; the prototype of §0 item 7 is the test. The loader already checks that a contributor is the owner or a dependant and validates the entry schema. `GET /organisation-types` returns the registered entries (labels in the caller's locale, with the other locales). A stored organisation whose type is no longer registered (a profile that dropped the contributing module) is still listed and readable and shows `typeKnown: false`; it cannot be written to until the type is back.
4. **`org.usage` registry** (declared by this module; Decision 9). An entry is `{ id, count(tx, organisationId) }` where `id` is the contributing module's id. Deleting an organisation, and changing its type, ask every entry; a count above zero is `409 organisation-in-use` and the problem names the contributing module ids but not the rows. M7 contributes the entry for `service_organisation`; M6 tests it with the fixture contributor of §0 item 7. Without a contributor nothing blocks (a registry-only deployment before M7).
5. **Tables and migration** (prefix `org_`, Decision 2; `pnpm db:generate --filter @scorpion/registry-organisations`). `org_organisation`: `id` (UUIDv7), `type` (text, not an enum; checked against the registry in the service), `abbreviation`, `name`, `description` (plain text, nullable), `website` (URL, nullable), `ror_id` (nullable), `same_as` (`text[]`, default empty), `contact_email` and `contact_type` (nullable, set together or not at all), `logo_blob_id` and `logo_hash` (nullable, filled in sprint 2; no foreign key), `created_at`, `updated_at`, `created_by`, `updated_by` (user ids, no foreign key). Constraints: unique `(type, lower(abbreviation))` and unique `(type, lower(name))` (the legacy editor skipped a duplicate name or abbreviation; here it is a clear 409), unique `ror_id` where it is not null (an ROR id names one organisation), length checks (abbreviation 1 to 64 with no whitespace or `/`, name 1 to 200, description at most 4000, website an `http(s)` URL at most 500, `contact_type` 1 to 64, `contact_email` at most 254), an index for the case-insensitive search. Nothing in the database depends on the list of types, so a new type needs no migration. A test fails for any `pgEnum` and for a table without the prefix (ADR-0004 checks the second at start).
6. **Field validation** (pure, `service/fields.ts`, table-driven tests; the Zod schemas of the routes use it):
   1. `sameAs`: at most 20 entries (a named constant, tested), each an `http(s)` URL of at most 500 characters, no credentials in the URL, no whitespace, no `javascript:`, `data:` or other scheme; trimmed, normalised the way the website is, duplicates removed, order kept. A URL is never fetched.
   2. ROR id: the stored form is the bare id and must match the ror.org pattern `^0[a-hj-km-np-tv-z0-9]{6}[0-9]{2}$` (a leading `0`, six characters of the Crockford base32 alphabet without `i`, `l`, `o`, `u`, two digits); the input may also be `https://ror.org/<id>` or `ror.org/<id>` and is normalised to the bare lower-case id; anything else is 422 naming the field. The checksum of the last two digits is verified too if the unit test with the published examples passes; if it does not, the pattern alone stays and the plan says so in ADR-0033.
   3. Contact point: `contact_email` is one syntactically valid address (the length check and a conservative pattern; no DNS or deliverability check), `contact_type` a short label from the schema.org vocabulary of contact types written as plain text (`customer support` style; the form offers suggestions, it does not enforce a list). A type without an address, or an address without a type, is 422.
   4. Everything is plain text; control characters are refused; HTML in a field is stored as text and escaped on output.
7. **Service layer** (`service/organisations.ts`; every method takes the `actor`): `list` (filters `q` over abbreviation and name with the `%`/`_` escape, `type`; sort `abbreviation` then `id`; page and `pageSize` capped at 100; each row also carries `memberCount` and, from sprint 3, `myMembership`; **a list row never carries the contact point or `sameAs`**), `get`, `create`, `update` (a partial body; `type` may change only while `org.usage` counts zero), `delete`. ## 7. Sprint 3: membership, managers and delegation

**Branch:** `feature/m6-membership`. **Goal:** a signed-in person can ask to join an organisation of a type that allows it; an administrator **or a manager of that organisation** decides, and a manager removes plain members of their own organisation (Decision 16); nobody decides on their own request or changes their own role; the requester gets the mail; `organisation.member` is a registered resource policy with delegated rights that M7 can build on.

Work items

1. **ADR-0034 first** (scoped permissions at the route, Decision 8, and the first delegated role, Decision 6), with the prototype of §0 item 8 and a prototype of the two route designs in a test before the ADR is written. The question from the backlog: the authorizer checks a permission that declares a `scope` globally, so an organisation manager who lacks it globally is denied at the route even though the policy would allow them. Content: M6 and M7 both use the pattern that needs **no pipeline change**: the route declares a plain global permission that everyone who may reach the resource family has (here `…organisation.read`), and the service calls `ctx.authz.require(actor, '<scoped permission>', { type, id })`, which consults the resource policy. The ADR records the alternative (a `scoped` flag on `createRoute()` that lets the pipeline pass a caller who lacks the permission globally, with the service re-check as the guard; it touches `packages/contracts/src/route.ts` and `apps/server/src/pipeline/**`, both ASVS-scoped) and says it is built in M7 only if `service.edit` cannot use the first pattern. It also records the delegation design (items 3 to 5): who may do what (decide, promote and demote, remove, and the edit of sprint 4 with its field rules and the route switch from `manage` to `read` for `PATCH` and the logo routes, Decisions 14 and 16, so the policy is designed once), the rules that cannot be delegated (own request, own role), and what happens to the last manager. Nothing in the pipeline changes in M6.
2. **`org_membership` table** (migration `0001`): `id`, `organisation_id` (foreign key to `org_organisation`, `on delete` restricted: the service removes the rows first), `user_id` (no foreign key), `state` (text with a check constraint over `requested`, `approved`, `rejected`, `left`; no pg enum), **`role` (text, check over `member`, `manager`, default `member`; `manager` only while `approved`, enforced by a check constraint and the state machine)**, `requested_at`, `decided_at`, `decided_by`, `ended_at`, `ended_by`, `role_changed_at`, `role_changed_by` (nullable), `created_at`, `updated_at`. **One row per `(organisation_id, user_id)`** (unique): a later request after a rejection or a leave reopens the same row (the role is reset to `member`) and the history is the audit trail of the events (Decision 5). Indexes for "my memberships", "pending, oldest first", "members of an organisation" and "managers of an organisation" (partial, `role = 'manager'` and `state = 'approved'`). Count queries group in SQL (`memberCount` of approved rows; no N+1).
3. **State machine** (`service/membership-state.ts`, pure, table-driven tested): `request` (none, `rejected` or `left` → `requested`; `requested` and `approved` are idempotent and answer the current row), `approve` and `reject` (`requested` only; `by: admin | manager`), `withdraw` (`requested` → `left`, by the member), `leave` (`approved` → `left`, by the member, a manager too; the role goes back to `member`), `remove` (`approved` → `left`, by an administrator, any member or manager, `by: 'admin'`, or by a manager of that organisation, a plain member only, `by: 'manager'`; never of oneself, that is `leave`; the role resets) and **`promote` / `demote`** (`approved` only: `member` ↔ `manager`; same role is idempotent; any other state is `Conflict` `membership-state`). Anything else is `Conflict` `membership-state` naming the state, never a 500. The table of transitions, with who may do each, is in the README and the ADR.
4. **Delegation rules** (Decision 6; ADR-0034). The role of a person is a property of their approved membership of **one** organisation.
   - **Who may decide a request** (approve or reject): an Admin (all organisations) and a manager of **that** organisation. A manager of organisation A has no right on organisation B (a test with two organisations).
   - **Who may promote or demote:** an Admin, or an existing manager of that organisation. Only an approved member can be promoted; a person with a pending request cannot.
   - **Who may remove an approved member (Decision 16):** an Admin (any member of any organisation, a manager too) and a manager of **that** organisation, for a **plain member** only. A manager cannot remove another manager (403, "Only an administrator can remove a manager."), cannot remove themselves (403, "Use leave to end your own membership."; an Admin who is a member is bound by it too), and has no right on another organisation. The role is re-read **under the row lock**, so a member promoted a moment before cannot be removed by a manager any more. A `requested` row is decided or withdrawn, never removed (409 `membership-state`). This is consistent with promote and demote: to end another manager's role a manager can only demote them (Decision 6; Remaining question 2, §13), which is a separate, audited and announced act.
   - **Nobody approves their own request:** the `approval` rule of `core.authz` denies it before roles and policies, Admins and managers included; the service passes `requestedBy` on every decision path. A manager who is also a requester of another organisation cannot approve that request either.
   - **Nobody changes their own role:** `setRole` throws `Forbidden('You cannot change your own role.')` when the target membership's user is the caller, whatever roles the caller holds (the check of `requireRoleChange` in `core.authz` is the model; it is repeated here in the module because it concerns a module's own data). A manager therefore cannot promote or demote themselves, and an Admin who is a member cannot make themselves manager; another Admin or manager can.
   - **Manager limit:** a promotion that would exceed `membership.maxManagersPerOrganisation` (setting, default 20, 1 to 100) is `Conflict` `too-many-managers`; it bounds the mail fan-out.
   - **The last manager** may leave or be demoted (by an Admin or by another manager; a lone manager cannot demote themselves). The organisation then **has no manager and falls back to administrators**: requests are decided and announced by Admins only until someone is promoted. The event carries `organisationHasManager: false`, the manager screen shows "No manager: administrators decide", and an inbox item goes to the administrators ("organisation X has no manager"; category `membership`, no mail). Nothing blocks the leave or the demotion.
   - **Two deciders at once:** every state or role change, a removal included, locks the membership row (`select … for update`) inside the transaction; the second caller sees the new state and gets `409 membership-state` (a decision) or an idempotent `200` (a role change to the role the row already has). A role change locks the target row first, then reads the manager count.
   - **Authorization is re-read per call.** The policy reads the caller's membership from the database on every call (no cache). A decision already past the policy check when a demotion commits is allowed once; the next call is denied (a test shows the next call is denied; the window is one request and is documented in ADR-0034).
5. **Service layer** (`service/memberships.ts`): `request(actor, organisationId)`, `withdraw`/`leave(actor, organisationId)`, `decide(actor, membershipId, 'approved' | 'rejected')`, `remove(actor, membershipId)`, `setRole(actor, membershipId, 'member' | 'manager')`, `listOwn(actor)`, `listForOrganisation(actor, organisationId, filters)`, `listPending(actor, filters)` and `summary(actor)` (list envelope for the lists). Rules:
   - `request`: the organisation exists, its type has `membership: true` (else 422 `membership-not-supported`), the caller has fewer than `membership.maxPendingPerUser` open requests (a setting, default 10; the answer is `Conflict` 409 with the problem type `too-many-pending`, not a 429, because waiting does not help), and the row is created or reopened in one transaction with its event, the recipients' mails and inbox items (item 8).
   - `decide`: loads the membership (404 if unknown), then `ctx.authz.require(actor, 'registry.organisations.membership.decide', { type: 'organisation', id: membership.organisationId, approval: true, requestedBy: membership.userId })`. Admin holds the permission globally; a manager holds it through the policy (item 6); the `approval` rule makes **an Admin or a manager deciding on their own request** a 403 whatever their roles (the rule of `core.authz`; this module does not re-implement it). The row is then locked (`for update`) and the state re-checked, so two deciders cannot both decide; the second answer is 409 `membership-state`. A decision writes `decided_by`, `decided_at` and the event (`by: admin | manager`), and enqueues the requester's mail and inbox item, all in one transaction.
   - `setRole`: `require(actor, '…membership.manage-roles', { type: 'organisation', id })`, then the own-role check, then the lock, the state check (`approved`) and the manager limit; writes `role`, `role_changed_at`, `role_changed_by`, the event `registry.membership.role-changed@1` and an inbox item to the person whose role changed (no mail), in one transaction.
   - `remove`: loads the membership (404), then `require(actor, '…membership.remove', { type: 'organisation', id: membership.organisationId })` (Admin globally, a manager through the policy); then the own check (the target's user is the caller: 403, use `leave`), the lock (`for update`), the state check (`approved`, else 409 `membership-state`) and the role check **under the lock** (a manager target needs the Admin permission held globally, else 403); writes `ended_at` and `ended_by`, resets the role and emits `registry.membership.left@1` with `by: admin | manager`, and, when the organisation is left without a manager, the inbox item of item 4, all in one transaction. The removed person gets no mail (backlog; the same line as the Admin removal).
   - `leave`, `withdraw` and `listOwn` act only on the caller's own row (the actor id, not a parameter); another person's membership id answers like an unknown one (404), the own-data pattern of M4b sprint 1.
   - `listPending` and `listForOrganisation`: an Admin sees every organisation; a manager sees **only the organisations they manage** (the service computes the managed ids from the database; a request for another organisation is 403 on `listForOrganisation` and simply absent from `listPending`); anyone who is neither is **403** (the same answer a plain User gets today for any administrative list, so the defect-1 matrix keeps its meaning). ## 13. Decisions taken (follow-up, 2026-10-09)

The maintainer answered the four points that the decisions of §15 had created. They continue the numbering of §15 (Decisions 14 to 17); "Decision n" in the sprints means §15 or this section.

14. **Admins and the managers of an organisation edit the organisation record.** Managers edit the descriptive fields of their **own** organisation; **an Admin edits every field and alone creates and deletes organisations**; managers never write `type`, `abbreviation` or `name`, and never create or delete. _Reason:_ organisations should look after their own description and contact; type, abbreviation and name are the identity of the record: `type` drives membership, the `org.usage` check and the profile's `@type`, the abbreviation is the lookup key M7 and M8 use (`findByAbbreviation`), and the name is unique per type and appears wherever a service names its organisation, so a change by a non-Admin could break references. _Changed:_ a second editor group, built as a service-level scoped check with the `organisation.member` policy (the route carries the global `…organisation.read`, ADR-0034): sprint 1 item 7 (the field-rules table, with Admin the only group), sprint 3 (the policy exists), **sprint 4 item 1** (the scoped permission `…organisation.edit`, `update` and the logo path with `requiredAccess`, the route switch, `editableFields`), item 2 (events and audit with `by`), item 3 (field tables, V8), sprint 5 item 1 (the manager's edit form on `/account/organisations`), journey 7, the risk rows and the acceptance rows. The rules per field:

    | Field                                                 | Read                                                                                                  | Write                                                              |
    | ----------------------------------------------------- | ----------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
    | create and delete an organisation                     | not applicable                                                                                        | **Admin only** (`…organisation.manage`); a manager is 403          |
    | `type`, `abbreviation`, `name`                        | every signed-in person                                                                                | **Admin only** (`manage`); a manager is 403, request refused whole |
    | `description`, `website`, `sameAs`, `rorId`           | every signed-in person                                                                                | Admin, and a manager of that organisation (`…organisation.edit`)   |
    | `logo`                                                | every signed-in person (the file is public by hash)                                                   | Admin, and a manager of that organisation                          |
    | contact point (`contact_email`, `contact_type`)       | Admin and the managers of that organisation always; other signed-in persons by the setting (sprint 2) | Admin, and a manager of that organisation                          |
    | `memberCount`, `created_by`, `updated_by`, timestamps | `memberCount` every signed-in person; the rest Admin                                                  | nobody (set by the service)                                        |

    An Admin is never restricted from any field, from create or from delete (`org.usage` and the uniqueness rules apply to everyone alike). A person who is neither an Admin nor a manager of that organisation writes nothing. Both groups pass the same validation and limits.

15. **Anonymous access to the profile and the contact point: signed-in only in M6; in M7 a public read for organisations that have services.** The M7 route serves the profile **without `contactPoint`** for organisations that at least one service references (the exact rule is M7's). _Reason:_ M6 stays free of public routes and of the question what "referenced" means before services exist; the `org.usage` registry already answers it later. _Changed:_ sprint 2 items 2 and 6 (wording), §10, §11 (the note for M7 and M8 and the proposed entry text for `docs/backlog.md`), §12, the acceptance and risk rows. The earlier recommendation "anonymous read in M8" is replaced.
16. **Managers may remove plain members of their own organisation.** Not other managers (only an Admin removes a manager), not themselves (that is `leave`; an Admin who is a member is bound by it too). The route carries the global `…organisation.read` and the service requires the scoped `…membership.remove`; the role is re-read under the row lock. The event is `registry.membership.left@1` with `by: manager` next to `by: admin`; both are `critical`. _Reason:_ without it a manager can demote an abusive member but not end the membership. _Changed:_ sprint 3 items 3 to 6, 10, 12 and 13, the removal tests (cross-organisation, a manager target, the own row, two removals at once, a removal racing a decision or a promotion), the V8 evidence, journey 4, sprint 5 items 1 and 2. This replaces "Admin-only `remove`".
17. **One audited `{@html}` for the JSON-LD block.** One component `JsonLd.svelte` whose only input is the output of `serializeJsonLd`; the lint exception is limited to that one file; a hostile-input test; a sentence in ADR-0033. _Reason:_ a data block must be written unescaped into a `<script>`; the escaping function is the one control and it is tested. _Changed:_ sprint 4 item 7, §2, the acceptance and risk rows. The `transformPageChunk` hook step stays the fallback only if the prototype of sprint 4 item 7 fails.

### Remaining questions

Two small points that the follow-up created; none blocks sprint 1. The plan follows the recommendations until they are answered.

1. **Do edits by managers of the ROR id, the website and the `sameAs` links need an Admin's review?** These are external identity claims shown to every signed-in person and, from M7, to the public. A wrong ROR id also blocks the real organisation from using it (the id is unique). Decision 14 allows managers to write them. _Recommended:_ no review step in M6; keep the edit as decided, with `by: manager` entries on the critical audit channel, `updated_by` shown to Admin, and a backlog item for a review queue and an inbox item to administrators. Answer before sprint 4.
2. **May a manager demote another manager?** Decision 6 lets an Admin or an existing manager promote and demote; Decision 16 lets only an Admin remove a manager. Together a manager can end another manager's role in two steps (demote, then remove the now plain member). _Recommended:_ keep Decision 6 as decided (the steps are separate, audited and `critical`, and the Admin can always reinstate); if the maintainer wants a manager to be unremovable by anyone but an Admin, make demotion of another manager Admin-only, which is one row in the policy table and one test. Answer before sprint 3.

## 15. Decisions taken (2026-10-09)

The maintainer answered every open decision of the draft; the four points that the answers created are Decisions 14 to 17 in §13. Each entry shows the answer, a one-line reason, and what it changed in the sprints. The numbers follow the maintainer's list (draft Decisions 4 and 5 are merged into 4; the draft's 6 to 14 are now 5 to 13). References in the sprints to "Decision n" use these numbers.

1. **Profile `registry` now.** The seven core modules plus `registry.organisations`; services in M7, `public-api` in M8; the CI image matrix and the ghcr publish matrix get a leg each; ADR-0032. _Reason:_ a neutral name (no operator name in the repository, ADR-0030) and an image for Gate 2 to test early. _Changed:_ sprint 1 item 9 and the definition of done (image published from the first merge).
2. **Table prefix `org_`** through the manifest's `tablePrefix`. _Reason:_ short names, as `core.audit` does with `audit_`. _Changed:_ sprint 1 items 2 and 5; sprint 3 item 2 (`org_membership`).
3. **Organisation types are a code registry `org.type`, not a vocabulary.** _Reason:_ a type carries behaviour (`membership`, now also `schemaType`), and M7 depends on it. _Changed:_ sprint 1 item 3; `schemaType` added to the entry (sprint 2 item 3).
4. **Lean fields plus a Schema.org `Organization` profile.** Fields: type, abbreviation, name, plain-text description, website; unique per type, case-insensitively; pages by id at `/organisations/:id`; the abbreviation stays the lookup key for M7 and M8. In addition (a) JSON-LD in the detail page, rendered on the server, CSP-safe, escaped; (b) a route that returns `application/ld+json`; (c) stored `sameAs` list and ROR id, logo through the blob store, contact point (email, contact type). Not chosen: `parentOrganization` and any hierarchy. _Reason:_ the organisation must be machine-readable and linkable to external identifiers without a second model. _Changed:_ a new **sprint 2** (the profile and the logo); sprint 1 item 5 and 6 (columns, validation); §3 (the mapping table); sprint 2 items 1 to 6 (builder and escaping, a dedicated route rather than content negotiation, the logo flow with replace and delete cleanup, the answer to the `core.blob` upload question, contact visibility); sprint 4 items 5 to 7 (the logo form, the detail page, the JSON-LD block); the contact point and logo in the field tables (sprint 4 item 3); Decisions 15 and 17 (§13).
5. **Membership model.** One row per person and organisation, reopened by a later request; the history is the audit trail; an administrator's removal is `approved → left` with `by: 'admin'` in the event; a cap of 10 open requests per person (a setting). _Reason:_ no extra state and no history table to teach to M13. _Changed:_ sprint 3 items 2, 3 and 5.
6. **Deciding is delegated to organisation managers** (different from the recommendation). The membership gets a role (`member` | `manager`); an Admin or an existing manager of that organisation promotes and demotes; a manager approves and rejects requests of their own organisation and sees them; Admin keeps the global right; nobody approves their own request or changes their own role; the last manager may leave or be demoted and the organisation falls back to Admin; two deciders at once are serialised by a row lock; the check is a service-level scoped check with the `organisation.member` policy and the routes carry a plain global permission. _Reason:_ organisations should run their own membership; the maintainer decided it is worth the extra design. _Changed:_ a new **sprint 3** content (role column, `promote`/`demote`, manager limit setting, the `manage-roles` and `read-contact` scoped permissions, the policy table, the `role-changed` event, routing of mails and inbox items to managers and administrators, the purge of managers, the V8 evidence plan with tagged tests); the manager section, the card and journey 4 in sprint 5; the prototype of §0 item 8; the delegation risks; the acceptance rows.
