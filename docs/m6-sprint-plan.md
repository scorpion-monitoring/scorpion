# M6 Sprint Plan: `registry.organisations`

Status: proposed, 2026-10-09. Decisions 1 to 14 (§10) wait for the maintainer; each has a recommendation, and the plan follows the recommendations until they are answered.
Scope source: [implementation.md](implementation.md) §4, M6, and the Gate 2 line that asks for a registry profile "added by M6, ADR-0030". Closes no defect of FEATURES §5; it builds on defect 1 (every route has a permission) and prepares defect 2 and 14 for M7 (the organisation side of the service ↔ consortium link). Releases as `0.8.0` (`0.7.0` is M5, released 2026-10-09, see [m5-sprint-plan.md](m5-sprint-plan.md)). Gate 2 follows M8.

M6 is size M (about 2 to 3 weeks for one developer). It is the first module that is **not** a `core.*` module: the first one that contributes to the registries of the core (`authz.resourcePolicy`, `authz.defaultRole`, `notify.template`, `ui.routes`, `ui.nav`, `ui.widget`), declares a registry of its own (`org.type`, `org.usage`), and is added to a profile that is not `core-only`. Everything it needs exists since M5; the risk is not new infrastructure but getting the first plugin's conventions right, because M7 to M17 copy them. This plan splits M6 into three sprints of about one week, each one `feature/m6-*` branch and one pull request into `dev`. M6 is released once, after sprint 3.

## 2. Cross-sprint rules

- Stay inside M6. Anything else goes to `docs/backlog.md` (§9). Services, the service wizard, the catalogue and the public API are M7 and M8.
- **One pull request per sprint** (CLAUDE.md "Working style"). ADRs, READMEs, backlog lines, the generated route table and review fixes go into the sprint's pull request. Push and open it when the sprint is complete and verified locally: `pnpm check`, `pnpm test --filter @scorpion/registry-organisations` and the packages touched, the full `pnpm test` before the last sprint, `pnpm test:e2e` for the journeys that exist.
- **Module rules** (CLAUDE.md): one package `modules/registry-organisations` with `module.ts` and `public.ts`; dependencies only in `package.json` (`core.authz`, `core.settings`, `core.identity`, `core.notifications` as dependencies; `core.ui-shell` as an optional peer, so the module starts in a profile without the shell); layers `ui/` → `routes` → `service/` → `db/`; tables carry the prefix (Decision 2); foreign keys point only to the module's own tables. **No foreign key to `identity_user`**, as `core.authz` does, so a purge cannot be blocked.
- **No hard-coded lists.** Organisation types are a registry (`org.type`, Decision 3); the membership states are the state machine of the service, a closed set of code with a check constraint and no pg enum; limits (pending requests per person) are settings; every label comes from the message catalogue or the type entry's labels per locale. A test fails on a pg enum.
- **Layer rule 5:** the service layer is the only way to change data. The routes, the purge subscriber and (later) the migration tool call the same methods. Every write that touches more than one row runs in `ctx.db.tx()` and emits its event and its mail inside it.
- **A service method needs:** an integration test against real Postgres (Testcontainers), a denied-permission case, a rollback case for a multi-row write (a mail that cannot be stored rolls the membership change back), and, for membership, a concurrency case (two administrators decide the same request at once).
- **Pure logic gets table-driven unit tests:** the membership state machine (`transition(state, action, by)`), abbreviation and name normalisation, the type-entry check, the search escape (`%`, `_` and `\` in a query), the sort and page maths.
- **Routes** use `createRoute()` with a `permission`; every list uses the legacy envelope with 0-based pages and a stable sort (key, then id); invalid input is 422 and an unknown reference is 404 or 422, never 500; a new route gets an entry in the matrix of `apps/server/src/defect-01.privilege-escalation.test.ts`, a regenerated route table in `docs/security/authorization.md` (the test header says how), and `response-fields.test.ts` checks its schema by itself. There is no public route in M6 (§8); `public: true` is not used.
- **Security rules** (CLAUDE.md): check permissions twice (the route, and `ctx.authz.require(actor, permission, resource)` in the service for the resource-scoped ones); nobody approves their own request; no secret, token or session id in a log or an event; a mail never carries more than the template needs.
- **Scoped paths.** M6 plans **no change** to `modules/core-identity/**`, `modules/core-authz/**`, `apps/server/src/pipeline/**` or `packages/contracts/src/route.ts` (Decisions 9 and 11 keep it that way). It does change **`docs/security/**`**, which maps to all four chapters (implementation.md §8.4): the regenerated `authorization.md` and the new field tables are such a change. Each sprint that regenerates it carries either the matching update of `v8-authorization.yaml` (the notes of 8.1.1, 8.1.2 and 8.2.3 name the objects and the walker) or the label `asvs-no-impact` with a description line that starts exactly `ASVS impact: none because <reason>`. §6 and each sprint say which.
- **A module with events** is added as an optional peer of `core.audit` (`package.json`, README of `core.audit`) and gets entries in `decisions.ts` in the same sprint; `decisions.test.ts` fails otherwise.
- Use the factories in `packages/testing`; add `makeOrganisation` and `makeMembership` there. Never hand-write fixture SQL.
- Update the module README in the same commit as every manifest change (permissions, settings, events, registries, routes). `core.notifications` and `core.audit` READMEs change where this plan says so.
- A test never calls a third party. No new runtime dependency is expected (Drizzle, Hono, Zod, the existing kernel and ui-kit are enough); if one appears, the pull request description names it and says why.
- Every pull request carries a changeset (package `scorpion`), written for operators and API users: the new module, the new profile and image, the new permissions and routes, what an administrator can now do. Sprint 1 and 2 are `minor` changesets; the release turns them into `0.8.0`.

2. **Create `modules/registry-organisations`:** `module.ts` (a `defineModule` manifest, id `registry.organisations`), `public.ts`, `README.md`, `package.json` (`@scorpion/registry-organisations`, exports `./module`, `./public`, `./ui`), `tsconfig.json`, `db/schema.ts`, `migrations/`, `routes.ts`, `service/`, `settings-schema.ts`. Run `pnpm modules:sync` so `defineProfile()` knows the id. Copy the shape of `modules/core-audit` (manifest closure around the service, `module.test.ts` that checks the manifest, README with the tables of permissions, routes, events, registries, settings).
3. **`org.type` registry** (declared by this module; Decision 3). An entry is `{ id, labels: { en, de? }, membership: boolean, order }`: `id` is a lower-case key (`provider`), `labels` are shown by the UI, `membership` says whether people may become members of an organisation of this type. The module contributes `provider` and `consortium` itself (both `membership: true`, as FEATURES §3.4 and M6's "consortium membership too" ask). A second module can add `funder` (`membership: false`) without editing this one; the prototype of §0 item 7 is the test. The loader already checks that a contributor is the owner or a dependant and validates the entry schema. `GET /organisation-types` returns the registered entries (labels in the caller's locale, with the other locales). A stored organisation whose type is no longer registered (a profile that dropped the contributing module) is still listed and readable and shows `typeKnown: false`; it cannot be written to until the type is back.
4. **`org.usage` registry** (declared by this module; Decision 10). An entry is `{ id, count(tx, organisationId) }` where `id` is the contributing module's id. Deleting an organisation, and changing its type, ask every entry; a count above zero is `409 organisation-in-use` and the problem names the contributing module ids but not the rows. M7 contributes the entry for `service_organisation`; M6 tests it with the fixture contributor of §0 item 7. Without a contributor nothing blocks (a registry-only deployment before M7).
5. **Tables and migration** (prefix `org_`, Decision 2; `pnpm db:generate --filter @scorpion/registry-organisations`). `org_organisation`: `id` (UUIDv7), `type` (text, not an enum; checked against the registry in the service), `abbreviation`, `name`, `description` (plain text, nullable), `website` (URL, nullable), `created_at`, `updated_at`, `created_by`, `updated_by` (user ids, no foreign key). Constraints: unique `(type, lower(abbreviation))` and unique `(type, lower(name))` (the legacy editor skipped a duplicate name or abbreviation; here it is a clear 409), length checks (abbreviation 1 to 64 with no whitespace or `/`, name 1 to 200, description at most 4000, website an `http(s)` URL at most 500), an index for the case-insensitive search. Nothing in the database depends on the list of types, so a new type needs no migration. A test fails for any `pgEnum` and for a table without the prefix (ADR-0004 checks the second at start).
6. **Service layer** (`service/organisations.ts`; every method takes the `actor`): `list` (filters `q` over abbreviation and name with the `%`/`_` escape, `type`; sort `abbreviation` then `id`; page and `pageSize` capped at 100; each row also carries `memberCount` and, from sprint 2, `myMembership`), `get`, `create`, `update` (a partial body; `type` may change only while `org.usage` counts zero), `delete`. Rules: `core.authz` `require` first; the body is normalised (trimmed, internal whitespace collapsed) and validated by Zod; a duplicate is `Conflict` with the field name; an unknown type is `Invalid` (422) naming the path; an unknown id is `NotFound`; `delete` runs `org.usage`, then removes the row (and, from sprint 2, its memberships) in one transaction. Each write emits `registry.organisation.created@1`, `registry.organisation.updated@1` (with the names of the changed fields, never the text) or `registry.organisation.deleted@1` through the outbox in the same transaction, and sets `updated_by`.
7. **Public service** (`public.ts`, for M7, M8 and later modules): `OrganisationsService` with trusted reads that check no permission and name nobody: `findByIds(ids)`, `findByAbbreviation(type, abbreviation)`, `exists(id)`, `listTypes()`, and (sprint 2) the membership reads. ## 5. Sprint 2: membership

**Branch:** `feature/m6-membership`. **Goal:** a signed-in person can ask to join an organisation of a type that allows it, an administrator decides, nobody decides on their own request, the requester gets the mail, and `organisation.member` is a registered resource policy that M7 can build on.

Work items

1. **ADR-0034 first** (scoped permissions at the route, Decision 9), with a prototype of the two designs in a test before the ADR is written. The question from the backlog: the authorizer checks a permission that declares a `scope` globally, so a provider member who lacks it globally is denied at the route even though the policy would allow them. Recommended content: M6 and M7 both use the pattern that needs **no pipeline change**: the route declares a plain global permission that everyone who may reach the resource family has (here `…organisation.read`), and the service calls `ctx.authz.require(actor, '<scoped permission>', { type, id })`, which consults the resource policy. The ADR records the alternative (a `scoped` flag on `createRoute()` that lets the pipeline pass a caller who lacks the permission globally, with the service re-check as the guard; it touches `packages/contracts/src/route.ts` and `apps/server/src/pipeline/**`, both ASVS-scoped) and says it is built in M7 only if `service.edit` cannot use the first pattern. Nothing in the pipeline changes in M6.
2. **`org_membership` table** (migration `0001`): `id`, `organisation_id` (foreign key to `org_organisation`, `on delete` restricted: the service removes the rows first), `user_id` (no foreign key), `state` (text with a check constraint over `requested`, `approved`, `rejected`, `left`; no pg enum), `requested_at`, `decided_at`, `decided_by`, `ended_at`, `ended_by` (nullable), `created_at`, `updated_at`. **One row per `(organisation_id, user_id)`** (unique): a later request after a rejection or a leave reopens the same row and the history is the audit trail of the events (Decision 6). Indexes for "my memberships", "pending, oldest first" and "members of an organisation". Count queries group in SQL (`memberCount` of approved rows; no N+1).
3. **State machine** (`service/membership-state.ts`, pure, table-driven tested): `request` (none, `rejected` or `left` → `requested`; `requested` and `approved` are idempotent and answer the current row), `approve` and `reject` (`requested` only), `withdraw` (`requested` → `left`, by the member), `leave` (`approved` → `left`, by the member) and `remove` (`approved` → `left`, by an administrator; the event carries `by: 'admin'`). Anything else is `Conflict` `membership-state` naming the state, never a 500. The table of transitions is in the README and the ADR.
4. **Service layer** (`service/memberships.ts`): `request(actor, organisationId)`, `withdraw`/`leave(actor, organisationId)`, `decide(actor, membershipId, 'approved' | 'rejected')`, `remove(actor, membershipId)`, `listOwn(actor)`, `listForOrganisation(actor, organisationId, filters)` and `listPending(actor, filters)` (list envelope). Rules:
   - `request`: the organisation exists, its type has `membership: true` (else 422 `membership-not-supported`), the caller has fewer than `membership.maxPendingPerUser` open requests (a setting, default 10; the answer is `Conflict` 409 with the problem type `too-many-pending`, not a 429, because waiting does not help), and the row is created or reopened in one transaction with its event, the admin mails and the admin inbox items.
   - `decide`: `ctx.authz.require(actor, 'registry.organisations.membership.decide', { type: 'organisation', id, approval: true, requestedBy: membership.userId })`. The `approval` rule makes **an Admin deciding on their own request** a 403 whatever their roles (the rule of `core.authz`; this module does not re-implement it). Concurrency: the row is locked (`for update`) so two administrators cannot both decide; the second answer is 409 `membership-state`. A decision writes `decided_by`, `decided_at` and the event, and enqueues the requester's mail, all in one transaction.
   - `remove`: `…membership.decide` with the same resource; a member cannot remove themselves through it (that is `leave`).
   - `leave`, `withdraw` and `listOwn` act only on the caller's own row (the actor id, not a parameter); another person's membership id answers like an unknown one (404), the own-data pattern of M4b sprint 1.
   - `listForOrganisation`: see item 6.

## 10. Decisions for the maintainer

None of these is assumed silently: the plan follows the recommendation until the maintainer answers, and each answer is recorded in the ADR named. Decisions 1, 2, 3 and 9 block sprint 1 or 2; the rest can be answered while the sprint runs.

1. **The registry profile: name and modules (blocks sprint 1; ADR-0032).** Recommended: **`registry`**, the seven core modules plus `registry.organisations` now, `registry.services` in M7 and `public-api` in M8; a neutral name, because no operator name belongs in the repository (CLAUDE.md rule 9) and the example columns of the architecture (`denbi-registry`, `nfdi-onboarding`) were removed on purpose by ADR-0030. `full` grows with every module. The CI `image` and `publish` matrices get one leg each; an image `dev-registry` is published from the first merge, although it holds only organisations until M7. Alternatives: `denbi-registry` (a deployment name in the repository), or no profile until M7 (the matrix change then rides with a bigger pull request and Gate 2 has no image to test early).
2. **Table prefix.** Recommended: the manifest sets `tablePrefix: 'org_'` (tables `org_organisation`, `org_membership`), as `core.audit` sets `audit_`; short, and the architecture already calls them `organisation` and `membership`. The default would be `registry_organisations_` (ADR-0004), which makes table names such as `registry_organisations_organisation`.
3. **Organisation types are a code registry, not a vocabulary.** Recommended, as the approved architecture says (`org.type` owned by `registry.organisations`, seed types provider and consortium, `funder` as an example): an administrator cannot add a type at runtime; a module contributes one at build time. A vocabulary would let an administrator add types, but the types carry behaviour (`membership: true or false`; later, which fields a type has) and M7's service roles (`provider`, `consortium`) depend on them. A vocabulary is the better fit only if operators must add types without a rebuild; say so now, because it changes sprint 1's schema.
4. **What an organisation has in M6.** Recommended: type, abbreviation, name, a plain-text description and a website. FEATURES §3.4 lists only abbreviation and name; "detail pages" need a little more. No logo (it needs the blob flow and the `core.blob.manage` permission question of M5), no ROR id, no hierarchy; abbreviation and name unique per type, case-insensitively (the legacy rule was global and silent, a provider and a consortium may reasonably share a short name).
5. **What the URLs and the public key are.** Recommended: pages use the id (`/organisations/:id`); the abbreviation stays a lookup key for M7 and M8 (`provider=` filters in v1 take abbreviations). A renaming therefore never breaks a link, and no redirect machinery is needed (M7's service slug is different). Alternative: abbreviation in the URL, which is prettier and needs rename redirects.
6. **Membership model.** Recommended: one row per organisation and person; a later request reopens the row; the history is the audit trail (events carry the states); an administrator's removal is `approved → left` with `by: 'admin'` in the event, no extra state; a cap on open requests per person (default 10, a setting) and nothing stronger against repeated requests after a rejection. Alternative: a history table or a `removed` state, which M13's mapping of legacy memberships would also have to know.
7. **Who may decide.** Recommended: **Admin only** (`…membership.decide`), as in the legacy app and in FEATURES §3.4; Reviewer reads organisations and nothing else here. Delegating to the members of an organisation (organisation admins) is a real product feature, not a small change, and goes to the backlog.
8. **The member list and the first resource policy.** Recommended: approved members of an organisation may see its member **usernames** and join dates (no email, no state), through the scoped permission `…membership.view-members` and the policy `organisation.member`, with a setting `membership.membersVisibleToMembers` (default on) that turns it off. It gives the policy a real use and a real test in M6 instead of only M7. Alternative: no member list for members (counts only, as the legacy app showed); the policy is then registered and tested through `isApprovedMember` and a test-only route, and sprint 2 shrinks.
9. **Scoped permissions at the route (ADR-0034).** Recommended: decide it in M6 as the backlog asks, but **build nothing in the pipeline**: the route carries a plain global permission and the service checks the scoped one (item 6 of sprint 2), the pattern CLAUDE.md already prescribes. Build a `scoped` route flag in M7 only if `service.edit` needs it. That keeps every ASVS-scoped path unchanged in M6. Alternative: build the flag now (changes `packages/contracts/src/route.ts` and `apps/server/src/pipeline/**`, so V7 and V8 entries and tagged tests change with it, and the sprint grows by about three days).
10. **Deleting an organisation.** Recommended: blocked with `409 organisation-in-use` while any contributor of `org.usage` counts a reference (M7 contributes the services entry); memberships do not block it and are deleted with the organisation in the same transaction, after a confirm that says so. Alternative: also refuse while approved members exist, which makes removing an unused organisation a two-step job for every old test entry.
11. **Where the member screens live.** Recommended: a page of this module at `/account/organisations` in the `account` section (what the legacy "profile → groups" screen did), because adding a section to the profile page would need either a slot in the identity profile page (a change in a scoped path) or the identity module knowing about organisations (a forbidden dependency direction). A slot for module sections on the profile page goes to the backlog.
12. **Which mails are mandatory and who gets an inbox item.** Recommended: both templates stay in the optional category `membership` as shipped, so a person who turned the category off gets neither the mail nor the inbox copy; administrators get an inbox item for a request (as for a registration request) and the requester gets one for the decision. Alternative: the decision mail is mandatory (the person cannot otherwise learn the outcome except by visiting the page).
13. **Release number and shape.** Recommended: `0.8.0` as a `minor` release after sprint 3, with the three images built by the tag push; no deploy is planned (the dev VM runs `core-only`). Alternative: release after sprint 2 as `0.8.0` and ship the UI as `0.9.0`, which splits M6's acceptance across two releases and contradicts "every milestone ends with a release".
14. **Stale profile names in `CLAUDE.md`.** Its layout line lists `full, denbi-registry, nfdi-onboarding, kpi-tracker` and its command example runs `PROFILE=kpi-tracker pnpm dev`, which ADR-0030 removed. Recommended: fix both lines (and the architecture table column) in sprint 1's pull request together with the new profile. The file is the maintainer's instruction text; say no if it must stay untouched.
