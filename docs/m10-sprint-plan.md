# M10 Sprint Plan: `kpi.ingestion`

Status: **decided**, 2026-10-19. The maintainer answered eight questions while this was drafted (all recorded in §13).
Scope source: [implementation.md](implementation.md) §5, M10, [architecture.md](architecture.md) (the `kpi.ingestion` rows of the module, registry and job tables), FEATURES §3.7 (data ingestion), §3.16 (`/api/v1/measurements`) and defect 6 (measurements) ([FEATURES.md](FEATURES.md) §5), and what M9 hands over (the RIMO `rimo:KPIValue` node, the effective KPI set, the value types, the backlog entries "No history of a service's KPIs" and "For M10").

M10 is size L in `implementation.md`. This plan has **five sprints (about five to six weeks for one developer)**. It is the first milestone that **writes** through the public API, the first with a **file upload** that is parsed, and the first with **two new runtime dependencies** (XLSX). Releases as `0.12.0` (`0.11.0` is M9, released 2026-10-19). Gate 3 follows M13.

## 2. Cross-sprint rules

- **One pull request per sprint** (CLAUDE.md). ADRs, READMEs, backlog lines, the regenerated OpenAPI document and review fixes go into the sprint's pull request; push when the sprint is complete and verified (`pnpm check`, the tests of every package touched, `pnpm test:contract`, the e2e of any journey changed, `pnpm openapi:diff`).
- **The module is `kpi.ingestion`** (`modules/kpi-ingestion`, package `@scorpion/kpi-ingestion`, table prefix `kpii_` set in the manifest). It depends on `core.authz`, `core.settings`, `core.notifications`, `registry.services`, `registry.organisations` and `kpi.framework`. Nothing depends on it before M11. It reads services, organisations and indicators only through their `public.ts`, and has **no foreign key** to a table it does not declare (`service_id` is a plain column; `indicator_id` points to `kpif_indicator`, a declared dependency, with `restrict`).
- **One domain path.** `upsertBatch()` in the service layer is the only way a measurement is written: the form, CSV, XLSX, the internal route and `POST /api/v1/measurements` all call it (defect 6, "two diverging code paths"). The migration tool of M13 will call it too.
- **Adapters are registry contributions.** The form, CSV/TSV and XLSX adapters are entries of `ingestion.adapter`; no `if (kind === 'csv')` in the module (CLAUDE.md rule 7). A later REST-pull or Matomo adapter is a contribution, not a change here.
- **A batch is all or nothing.** Any invalid row refuses the whole batch with one 422 that names every bad path (up to 100); nothing is written (FEATURES §3.7: "invalid cells block the commit").
- **Values are typed.** The registry decides the type (`numeric` or not); the table has a numeric and a text column and a check that exactly one is set; a value is stored in its canonical form (a duration as seconds). No value is stored as free text that a type could have checked.
- **Uploads are parsed in memory and never stored.** The file is read, turned into rows and dropped; the run keeps counts and at most 100 problems (row, column, a fixed code; a cell's content is never echoed beyond 64 characters), and a sanitised, bounded file name. Limits: a file at most 2 MiB (a route-level body limit), at most 5 000 data rows and 200 columns, an XLSX at most 20 MiB inflated and one sheet read (the first, or the one named). A formula is read as its cached value and never evaluated.
- **Output that a spreadsheet opens is escaped.** The import templates (CSV and XLSX) start every cell that begins with `=`, `+`, `-`, `@`, a tab or a carriage return with `'`, because indicator and service names are administrators' text.
- **Vocabularies and the registry are data.** Necessity, thematic category and units come from `core.settings`/`kpi.framework`; the module has no list of them. No hard-coded branding: the sender, the instance name and the link in the reminder come from settings.
- **Permissions are checked twice.** The route names a plain permission (`kpi.ingestion.v1.read`, `.v1.write`, `.measurement.read`) and the service calls `ctx.authz.require(actor, 'kpi.ingestion.measurement.submit', { type: 'service', id })` for the scoped one (ADR-0034). Nobody approves or changes their own role here, so no self-service rule arises.
- **Public v1 changes are additive** (`pnpm openapi:diff` against `v0.11.0`): two new routes and nothing else.
- **Transactions and events.** A batch runs in one `ctx.db.tx()` with its event in the outbox; every write method has a rollback test. The event names ids, periods and counts, **never a value** (a test checks it).
- **Time is injected.** "The current month" and "now" come from a clock the service takes, so month-end and future-period tests do not depend on the date they run on.
- **Update the module README with every manifest change.** A new **runtime** dependency is named in the pull request description and in ADR-0041 with its reason (Decision 1); the CSV parser is our own (Decision 5), and `fast-check` is a development dependency.
- Every pull request carries a changeset (package `scorpion`); sprints 1 to 5 are `minor` where an operator or API user can see something, `patch` otherwise.

## 3. The model

| Table                | Holds                                                                                                                                                                                                                                                                                                                                                                                                                            |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `kpii_measurement`   | `id` (UUIDv7), `service_id` (plain column), `indicator_id` (`kpif_indicator`, `restrict`), `period` (a date, **the last day of its month**; a check constraint enforces it), `value_numeric` (`numeric`), `value_text` (`text`, at most 4 000), exactly one of the two set, `source` (the adapter id, `api` for v1), `run_id` (`kpii_ingestion_run`, `set null`), audit columns. **Unique `(service_id, indicator_id, period)`** |
| `kpii_ingestion_run` | `id`, `service_id` (plain), `adapter`, `actor_id` (a user id kept as written), `file_name` (sanitised, at most 120), `status` (`committed`, `rejected`), `inserted`, `updated`, `unchanged`, `rejected`, `problems` (jsonb, at most 100 entries of `{ row, column, code }`), `started_at`, `finished_at`. A dry run is **not** stored                                                                                            |
| `kpii_reminder_sent` | `(provider_id, period)` unique, `sent_at`, `recipients` (a count): a retry of the job or a second node never mails twice for one provider and month                                                                                                                                                                                                                                                                              |

In `kpi.framework` (sprint 1, Decision 3): **`kpif_service_kpi_history`**, an append-only table `(service_id, set_id, extras, valid_from, valid_to)` written in the same transaction as `serviceKpis.set` and the wizard's `store`, with the current rows backfilled (`valid_from` = `updated_at`). It answers "which KPIs did this service have in this month" for M11 and M12 and is exposed as one tested query function (`kpisInPeriod(serviceId, period)`) on `kpi.framework/public`.

**Period.** `normalisePeriod(input)` (pure) accepts `YYYY-MM` and `YYYY-MM-DD` (any day of the month) and returns the last day of that month (leap years, 28, 29, 30 and 31 days); a date cell of an XLSX arrives as an ISO date. Anything else is a 422 that names the accepted forms. A period **after the current month** is refused (the clock is injected). Other date formats (`DD.MM.YYYY`, month names) are in the backlog, not in M10.

**What a service may report.** The indicators of its **effective KPI set now** (`serviceKpis.get`). A measurement for an indicator outside it is a 422 naming `rows[i].indicator`. Measurements of an indicator that the service has since dropped **stay** and are returned by the reads; the history above tells M11 which KPIs a month had.

**`upsertBatch(actor, serviceId, rows, { source, runId?, dryRun? })`** → `{ inserted, updated, unchanged, rejected, rows: [{ index, verdict }] }`: checks `measurement.submit` on the service, that the service exists, that each indicator is in the effective set, each value against its indicator's type and bounds (`valueType.schema(config)`), the period, and **duplicates inside the batch** (the same indicator and period twice is a 422, never "last wins"); writes with `insert … on conflict (service_id, indicator_id, period) do update … where the value differs` and counts inserted, updated and unchanged; emits `measurement.recorded@1` once per batch when something changed. A dry run does everything except the write and the event and returns the same verdicts.

**Events.** `measurement.recorded@1` is `{ serviceId, runId | null, periods[] (at most 120), inserted, updated, actorId }`. `kpi.impact` (M12) listens; nothing else does.

## 5. Sprint 1: the model, `upsertBatch`, the history

**Branch:** `feature/m10-measurement-core`. **Goal:** a measurement can be written and read through one tested service path, with every rule of defect 6 in place and no route yet.

Work items

1. **ADR-0041** (Decisions 1 to 5): the measurement model and the one write path, the XLSX dependency and its limits, the history of a service's KPIs, the permission and read rules, the own CSV parser. It also records the prototype results of §0 item 4.
2. **The module** `modules/kpi-ingestion` (manifest with `tablePrefix: 'kpii_'`, `public.ts`, README), added to the `full` profile only; `pnpm modules:sync` and `pnpm scorpion profile:generate full`. The loader's checks pass on the first run (prefix, dependencies, no foreign key outside the declared ones).
3. **Tables and migration** (§3): the check constraints (the period is a month end, exactly one value column, bounded text), the unique key, the `restrict` key to `kpif_indicator`. Constraint tests in the style of `kpi.framework`'s `db/constraints.test.ts`.
4. **`normalisePeriod`** and the value mapping (`numeric` → `value_numeric`, else `value_text`) as pure functions with table-driven tests (every month length, leap years 1900, 2000 and 2024, `2026-02-30` refused, `2026-13`, `26-01`, empty, whitespace, a time component).
5. **`upsertBatch`** as specified in §3, with the injected clock. Tests against real Postgres: **the same month twice updates and never duplicates** (the acceptance of `implementation.md`); an unchanged value counts as unchanged and emits no event; a duplicate row inside the batch, an indicator outside the effective set, an unknown indicator, a wrong type, a value out of bounds, a future period and an empty batch are 422 that name every bad path (never a 500); a rollback test (a failing outbox insert leaves no row); a denied case for each caller class (anonymous 401; a plain user, a member of another provider, a requested or left membership 403).
6. **The scoped permission** `kpi.ingestion.measurement.submit` (scope `service`) and its **resource policy** (an `authz.resourcePolicy` entry for the resource type `service`): Admin everywhere, and the **approved members** of the service's provider (Decision 2). This needs one **additive read on `registry.services/public`**, `isProviderMemberAsSystem(userId, serviceId)`, the sibling of `isProviderManagerAsSystem` (M9 sprint 3 added that one the same way). The policy asks at every call and caches nothing, so a removed member is refused at the next call (a test).
7. **The history** in `kpi.framework`: the table, the write inside `serviceKpis.set` and the wizard's `store`, the backfill migration, the query function `kpisInPeriod(serviceId, period)` on `public.ts` with property tests (a period inside, at the edge, before the first row, after a change, after two changes in one month), and a rollback test for the extended transactions. `kpi.framework`'s README and the event stay as they are.
8. **The in-use hook**: `kpi.framework` declares a registry `kpi.indicatorUsage` (a function from an indicator id to a count and a label) and its indicator delete asks it; `kpi.ingestion` contributes the count of measurements. The `restrict` key stays as the last guard. A test: an indicator with a measurement is 409 naming the module and the count; without one the delete works.
9. **The event** `measurement.recorded@1` declared and tested (no value in the payload; a test walks the schema).
10. **The prototypes** of §0 item 4 (throwaway, not committed; the results go into ADR-0041).
11. **README of the module**, the module's `docs/security/authorization.md` field table (the measurement and the run: who reads, who writes, what is never in an answer), the backlog, the changeset (`patch`: no route yet, but a migration runs at start).

ASVS impact (sprint 1): `docs/security/**` changes. **V8** gets a note and tagged evidence for the scoped permission (a member of another provider and a requested membership cannot submit: `[ASVS-8.2.1]`, `[ASVS-8.3.1]` style tags on the denial tests, never by editing an assertion); V6, V7 and V10 carry the `asvs-no-impact` line with a true reason. The maintainer's fields stay the maintainer's.

Tests (sprint 1): the pure functions (table-driven); `upsertBatch` with its denied, rollback and event cases; the constraints; the history and its property tests; the policy (a demotion and a removal are seen at the next call); the in-use hook; `defect-06.measurements-upsert.test.ts` (the same month twice is one row, a batch with a duplicate is refused, an unknown indicator is 422, nothing is written on a failure).

Definition of done: `pnpm check`, the tests of `kpi.ingestion` and `kpi.framework`, the full `pnpm test`, `pnpm security:asvs`, and the image module-set check for `full`, `core-only` and `registry` (the module is in `full` only).

**Amended in sprint 1 (what was decided while building it; the reasons and the prototype results are in [ADR-0041](adr/0041-measurement-model.md)):**

- **XLSX prototype passed, with a condition.** `read-excel-file` reads a normal file, a date cell (as a `Date` at UTC midnight), an empty trailing row, the **cached** value of a formula (a text formula answered its cached text, not its result) and refuses a truncated or non-zip file cleanly. It has **no inflation cap**: a 63 kB bomb that inflates to 60 MB ran 60 s and ended in a stack overflow. The adapter therefore needs the **guard** the plan allows (declared sizes from the central directory, then a bounded count while inflating in 4 KiB slices with `fflate`, for headers that lie): the bomb is refused in under 1 ms and a lying bomb after about 190 ms and 24 MB. Sprint 3 writes it before the first upload route. The fallback "no XLSX in M10" is **not** needed.
- **The XLSX dependency tree is larger than Decision 1 said:** `read-excel-file` 9.3.12 also depends on `worker-f` and `unzipper-esm` (`graceful-fs`, `node-int64`); `write-excel-file` 4.1.1 on `fflate`; eight packages in all. Its `node` entry parses in a worker thread, the `universal` entry in the calling thread. Sprint 3's pull request names all of it and chooses the entry. Nothing was added to the repository in sprint 1.
- **The write prototype passed:** a cookie `POST` on `/api/v1` without `X-CSRF-Token` is 401 (the check is in the authenticator for every method that is not safe, on every path); with it 200; a token and a stale cookie 200; a preflight from an origin that is not allow-listed 403. **No change to `apps/server/src/pipeline/**` is needed.**
- **A year before 1900 is refused** and **a batch covers at most 120 distinct months** (the event's `periods` holds 120); a one-time import chunks by ten years.
- **`upsertBatch` takes the indicator's id** (`rows[i].indicator`); resolving the legacy `kpi` name is the route's and the adapters' job (sprints 2 and 3), written once and shared.
- **A dry run answers a bad row as a `reject` verdict with its problems**, not as a 422; a batch wrong as a whole is refused in both modes.
- **The foreign key to `kpif_indicator` is written by hand** in the migration (Drizzle cannot name another package's table); the constraint and module tests prove it.
- **The history table has a primary key `(service_id, valid_from)`, no id column**, and an **append-only trigger** (the only update is closing the open row once). `kpisInPeriod` answers with the state at the **end** of the month and returns the effective rows of that state; `effectiveSet` was split into `effectiveSet` and `effectiveOf` so that the past and the present share one rule. The property tests use a seeded generator and an independent oracle; `fast-check` still arrives with the CSV parser (sprint 3).
- **`kpisInPeriod` has no `AsSystem` suffix**, as the plan names it, though it is a trusted read that checks no permission; a rename is in the backlog.
- **A token needs three scopes besides the route's** until `kpi.framework` offers a trusted read: `upsertBatch` reads the KPIs with `serviceKpis.get` and the bounds with `indicators.get` as the plan says, and both check the actor's plain read permission (probed: `submit` alone 403, `submit` and `set.read` 403, all three 200). **Sprint 2 decides this before it writes the route** (ADR-0041, decision 4).
- **`kpi.ingestion` declares only the dependencies it imports** (`core.authz`, `kpi.framework`, `registry.services`); `core.settings`, `core.notifications` and `registry.organisations` arrive with the sprint that needs them (the harness composes them as development dependencies).
- The factories `makeMeasurement` and `makeServiceKpiHistory` are in `packages/testing`; `defect-06.measurements-upsert.test.ts` is in the module (there is no route to go through yet; sprint 2's `defect-06.v1-measurements.test.ts` goes through the pipeline).

## 6. Sprint 2: the API

**Branch:** `feature/m10-measurement-api`. **Goal:** programs can write and read measurements through v1, and the signed-in UI has the reads it needs; every route has its contract test and its field table.

Work items

1. **`GET /api/v1/measurements?service=&indicators=&start=&stop=`** (`r.public('v1', …)`, permission `kpi.ingestion.v1.read`, `audit: true`, role `user` by default; Decision 4): the legacy time series with the **legacy envelope** `{ metadata, result }` (the legacy key was `data`; `result` is defect 6's fix) and 0-based pages. Rows keep the legacy names `kpi` (the indicator name), `value` and `date`, and add `id`, `indicatorId`, `iri`, `service` (the abbreviation), `period` and `valueNumber`. **`value` is the canonical text** the legacy API returned (`valueType.format`: a duration as `HH-MM-SS`, a number as a decimal string); `valueNumber` is the number or `null` for text. Sprint 2 checks this against the legacy API documentation (FEATURES §3.16) before the spec is committed: a v1 contract is hard to change. Stable order **across pages** (period, indicator name without case, then id; defect 6), `pageSize` at most 100 like every list, `totalCount` respects every filter (defect 15's rule), a `start` or `stop` in `YYYY-MM` or `YYYY-MM-DD`, an unknown service or indicator and a `start` after `stop` are 422 naming the parameter. `service` is required (a request for every service is an export, M11's).
2. **`POST /api/v1/measurements?service=`** (permission `kpi.ingestion.v1.write`, role `user`, `audit: true`): a body `[{ kpi, value, date }]` of at most 500 items (legacy shape; `kpi` is the indicator **name** without case or its id; `value` a string or a number; `date` `YYYY-MM` or `YYYY-MM-DD`), 200 with `{ inserted, updated, unchanged }`. It calls `upsertBatch` as the token's owner, so the scoped `measurement.submit` is checked in the service: **a token without write access to that service is 403** (the legacy "anyone with a key can write to any service" gap). A body over the limit is 413, an unknown service 422 naming `service`, an indicator outside the set 422 naming `[i].kpi`. A token needs the scope `kpi.ingestion.v1.write` **and** an owner who may submit (ADR-0015).
3. **Internal reads** for the submission page (`GET /kpi/measurements?service=&period=` and a read of the periods that have values, permission `kpi.ingestion.measurement.read`, role `user`): the grid of one month and the coverage of the last 12 months. They call the same service methods as v1.
4. **The CSRF and preflight checks** of §0 item 4 become tests. A session cookie on `POST /api/v1/measurements` without the CSRF header is refused (a tagged test `[ASVS-7.2.1]`); with it, it works as a person on the instance's own pages. If the pipeline needed a change, it is made here with its ADR and the V7 and V8 chapter files. The **preflight** for `/api/v1/measurements` names the methods of that path only (the backlog item "The preflight answer lists the methods v1 has overall"); if that needs `pipeline/cors.ts`, the same rule applies.
5. **Contract tests** with the harness for both routes (empty page, last page, `pageSize` over the total, stable order across pages, a token with and without the scope, `X-API-Key`, the walker green), and the cases the harness cannot know: a write is visible in the next read, writing twice is one row, **a form submission and an API call with the same data produce identical rows** (the acceptance of `implementation.md`; compared through the database, not the response), an unknown parameter is 422, a body that is not an array is 422.
6. **`defect-06.v1-measurements.test.ts`**: the ordering across pages (a series longer than a page, walked page by page, equals the one-page read), the envelope key, and the write permission (a token of another provider's member is 403, one of a member is 200).
7. **Documents:** `docs/security/authorization.md` (the field tables of the two v1 routes and the internal reads, the generated route table, what a measurement answer never holds: no actor id of another person, no file name, no run), the README, the OpenAPI document (`pnpm openapi:generate`), the backlog.

ASVS impact (sprint 2): V8 (the first v1 write: the pipeline checks scope and owner, the service checks the scoped permission), V7 (a cookie on a write, if the CSRF test finds a gap or the pipeline changes); V6 and V10 carry `asvs-no-impact`. **Amended in sprint 2 (what was decided while building it; the reasons are in [ADR-0041](adr/0041-measurement-model.md), "Amended in sprint 2"):**

- **A token needs `kpi.ingestion.v1.write` and `kpi.ingestion.measurement.submit`, and nothing of `kpi.framework`.** `kpi.framework` offers one additive trusted read, `effectiveIndicatorsAsSystem(serviceId)` (the effective rows with value type, unit, necessity and bounds, no permission check); `upsertBatch` uses it after its own scoped check and no longer calls `serviceKpis.get` or `indicators.get`. The sprint 1 test that named three scopes now names `submit` only, tagged `[ASVS-8.2.1] [ASVS-8.3.1]`.
- **A second trusted read was needed for the reads** (`indicatorsByIdAsSystem(ids)`: name, IRI, value type and unit by id), because a measurement of a dropped indicator stays and is read by name, and this module reads no table of another. It goes beyond the "one read" the maintainer named; it is recorded so it can be refused.
- **The names:** `resolveIndicatorRef` (`service/names.ts`, in `public.ts`) is the one function that turns a `kpi` name or id into an indicator of the effective set; `upsertByName` is the service method behind the route. Problems are named in the shape of the request (`[3].kpi`, `[3].value`, `[3].date`); Zod's own shape errors stay `3.kpi`.
- **The route resolves the service before the scoped check,** so an unknown service (id or abbreviation) is 422 naming `service` for anyone who may use the route; `upsertBatch` keeps 401, 403, 404, 422.
- **The body limit is 3 MiB** (`maxBodyBytes`; 500 items of 4 000 characters are 2.14 MB); the rate limiter counts requests, not items.
- **The preflight needed no change in `pipeline/**`:** `apps/server/src/preflight.ts` picks a `cors()` by path. The CSRF prototype became tests. No ASVS scoped path other than `docs/security/**` changed; V7 and V8 got a note and evidence.
- **The reads:** the time series ranks the service's indicators in memory and sorts by month, then that rank (`array_position`), so the order holds across pages; `start` and `stop` mean the month they name and may lie in the future; `indicators` may name the service's effective KPIs and every indicator it has a value for. The grid and the coverage are the internal reads: the coverage counts the effective indicators and those with the necessity term `mandatory` (the set as it is now) per month of the last 12 (at most 36).
- **The answer was compared with the legacy documentation** (FEATURES §3.16): it matches in path, parameters, row and envelope shape, and differs in `result` for `data`, the stable order, the write permission, `pageSize` at most 100 (default 100, not 1 000) and a required `service`; the legacy format of `date` and `value` is not documented and is recorded as a choice (ADR-0041, item 9; backlog "Measurement follow-ups (M10 sprint 2)").
- **Tests added beyond the plan:** the harness of `packages/testing` can now send a body and expect a write to answer differently the second time (`body`, `answersDiffer`); the contract test starts a second application with the limiter on; `apps/server/src/testing/identity-app.ts` has an `ingestion` option; `authorization-doc.test.ts` loads `kpi.ingestion` so the generated route table lists its four routes.

## 7. Sprint 3: the adapters

**Branch:** `feature/m10-adapters`. **Goal:** a person can turn a file or a form into rows, see what would happen, and commit; the registry, the parsers, the templates and the run history exist and are hardened. No page yet.

Work items

1. **The registry `ingestion.adapter`** (declared by this module, entries validated by a Zod schema at start; a clash of ids stops the start): `{ id, labels, accepts (extensions and media types), parse(input, context) → { rows: { indicator, period, value }[], problems[] } }`. `context` holds the service's effective KPI set (so a column can be matched by indicator name or IRI slug), the value types and the clock. An adapter never writes: it parses; `upsertBatch` writes.
2. **The form adapter**: input is `{ period, values: { [indicatorId]: string } }`; a blank value is "no value" (not an error unless the indicator is mandatory, and the form says so). It exists so that the page and the API share one path (the acceptance test of sprint 2 uses it).
3. **The CSV/TSV parser** (pure, in `service/csv.ts`, **no runtime dependency**, Decision 5): RFC 4180 quoting, embedded delimiters and newlines in quoted fields, doubled quotes, CRLF, LF and CR, a UTF-8 BOM, a trailing newline, delimiter detection between comma, semicolon and tab (a semicolon is common in German exports) with the extension as a hint, and the limits of §2 (rows, columns, field length 4 000). Table-driven tests plus **`fast-check` property tests**: any table of fields written with `writeCsv` parses back to itself; no input throws (every failure is a problem with a line and a column); a quote in the middle of an unquoted field and an unterminated quote are problems, not exceptions. `fast-check` is a development dependency, named in the pull request (the Scorecard fuzzing check is read first, as the backlog says).
4. **The XLSX adapter** (Decision 1: `read-excel-file` for the upload, `write-excel-file` for the template; both runtime dependencies, named in the pull request and ADR-0041): reads the first sheet (or the one the request names) as a table, date cells as ISO dates, formula cells as their cached value, merged cells as their top-left value; refuses a workbook over the inflated limit before inflating it (the pre-scan from the prototype), an encrypted one, one with more than the rows or columns limit; never follows an external link. Tests: a normal file, dates as dates and as text, a formula, an empty sheet, a zip bomb, a truncated file, a file with the wrong extension and the right type (the extension is a hint; the content decides, and a file that is neither is a problem, not a 500).
5. **The file adapters' mapping**: the first row is the header; each column maps to **Period** or to an indicator of the service (by id, by name without case, or by a name in the header that matches exactly one), each target at most once; the required ones are the period column and every **mandatory** indicator (the legacy rule), and the response says which are missing. The mapping is a parameter of the request (`{ column: string → 'period' | indicatorId }`); without one, the adapter proposes a mapping from the header and returns it with the preview.
6. **Preview, dry run, commit** (service level, one request shape for both): `ingestion.preview(actor, { serviceId, adapter, file | values, mapping? })` returns the header, the first 20 rows, the proposed or given mapping and the problems; `ingestion.run(actor, { …, dryRun })` parses again **from the same bytes** (the client never sends rows, so there is one trust path), runs `upsertBatch` with `dryRun`, and on `dryRun: false` writes and records the run. A dry run returns each row's verdict (`insert`, `update`, `unchanged`, `reject` with the code); the commit refuses the whole file when anything is rejected (a rejected run is recorded with its counts and problems, nothing else).
7. **`kpii_ingestion_run`**: written in the batch's transaction; `GET` of a service's runs (the last 50) and of one run; the file name is sanitised (a path, a control character, a very long name) and bounded; never the content.
8. **The import template per service**: `GET /kpi/ingestion/template?service=&format=csv|xlsx` (permission `kpi.ingestion.measurement.submit` on the service): a header row (the period, then every indicator of the effective set with a mandatory marker and unit in the header text) and one example row; **escaped against formula injection** (§2) and tested with names that start with `=`, `+`, `-`, `@`, tab and carriage return; the CSV is UTF-8 with a BOM so that a spreadsheet opens umlauts, the file name comes from the service's abbreviation, never from free text.
9. **The internal routes** for the page: `POST /kpi/ingestion/preview` and `POST /kpi/ingestion/runs` (multipart for a file, JSON for the form) with a **route-level body limit** (2 MiB; the `BodyLimitOverride` mechanism, one entry in the server's list: no change to `pipeline/**`), `GET /kpi/ingestion/runs`, the template route. Zod bounds on everything; a bad adapter id, a file with no rows and an empty form are 422, never 500.
10. **Documents:** the README (how to add an adapter, the limits, the template), `docs/security/authorization.md` (the run and the upload: who may, what is kept, what never), the backlog.

ASVS impact (sprint 3): V8 (the upload routes need the scoped permission in the service, not only the route), V7 none; V6 and V10 `asvs-no-impact`. The upload and parsing controls are **not** in a chapter the repository claims (V5 is not assessed); they are tested and described in the module README and ADR-0041 instead, so no claim is made that the badge does not cover.

Tests (sprint 3): the CSV parser (table-driven and `fast-check`); the XLSX adapter (the fixtures above); the mapping rules; `ingestion.run` with a denied case per caller class, a rollback case, a dry run that writes nothing (row counts before and after) and a commit that is refused whole; **the same data through the form adapter, the CSV adapter and the XLSX adapter gives identical rows**; the template tests (formula injection, umlauts, a service with no KPI set is 422); the internal routes through the pipeline (the body limit gives 413, the wrong service for a member 403).

Definition of done: as sprint 2, plus the image module-set check **and a look at the image size** (two runtime dependencies are added: the change against `0.11.0-full` goes into the backlog, as M9 did).

## 14. Decisions

Answered by the maintainer on 2026-10-19:

1. **XLSX uses `read-excel-file` (upload) and `write-excel-file` (template)** as runtime dependencies (MIT; `fflate`, `saxen`). `exceljs` was rejected as older and heavier; `xlsx` from npm is stale. The sprint 1 prototype must show that the library refuses a zip bomb and never evaluates a formula; if it cannot, XLSX leaves M10 and the backlog says so.
2. **Approved members of the provider, and Admin, may submit** measurements for a service (as the legacy page: "services of providers the user belongs to"). This differs from the KPIs of a service, which only managers change (M9).
3. **The KPIs a service had over time are recorded** in `kpi.framework` from sprint 1 (an append-only history written in the same transaction as every change), not derived from the measurements.
4. **Every holder of the read permission reads every service's measurements** (`kpi.ingestion.v1.read` and the internal read are held by the role `user`), as services and KPI definitions are readable by every signed-in person. Never anonymous, never public.
5. **The CSV/TSV parser is our own** (pure, no runtime dependency, `fast-check` tests); `csv-parse` was rejected.
6. **Values are not in the RDF read in M10.** The public pair and the model stay definitions only; M11's exporters may write the `rimo:KPIValue` node.
7. **No `kpi` deployment profile in M10** (the `full` profile carries the module).
8. **Five sprints.**

Taken by this plan, reversible without a migration (say if you disagree):

9. **A period after the current month is refused**, and a batch with the same indicator and period twice is refused (never "last wins").
10. **A batch is all or nothing**, and a dry run is stateless and never stored.
11. **The reminder runs on the 6th** (a setting, 1 to 28) for the previous month, to the approved members who may submit, once per provider and month.
