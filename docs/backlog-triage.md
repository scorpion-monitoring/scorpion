Every open line has exactly one row below.

## How it was made

Each line was read against the code at `dev` (two passes: a first pass over every line, then a stricter second pass over every "annoying" line and every unverified "nice to have" line). No code was changed for this table. The marks:

- **Class.** _breaks something_: the present code gives a wrong result, loses or leaks data, is a security or correctness gap, is a dead end for a user, or is a test that fails or flakes; the evidence column says how. _annoying_: it works but is awkward, slow, inconsistent, missing a guard, or costs maintainers time. _nice to have_: an enhancement, an optimisation without a shown problem, a design question, a deliberate scope limit. _record_: a measurement or a decision that needs no action (kept for history, not counted as work).
- **Size.** S: half a day or less, one place. M: one to three days, one module with tests or a migration. L: more, cross-module, or needs an ADR.
- **Verified.** `verified`: the code or the tests were read and the statement checked. `unverified`: it could not be checked from the repository (it needs a running system, production data, an outside service or a human decision) **or the check was not done in this pass**; the evidence column says which. Nothing is guessed: an unverified row carries the class its wording suggests and no more.

Limits: the passes were proportionate (a few tool calls per line), several "verified" rows rest on a search and not a full read of the surrounding code, and nothing was run. Treat the class of a "nice to have" row as a first reading.

## Recommended order for a later plan

1. **Done in M12a sprint 5.** **Stop the 429s (one sprint, `apps/server` and the loaders).** Three "breaks something" and "annoying" lines are one cause: the default rate bucket is keyed by address, so the shell's four reads on every navigation, the dashboard's reads and the data-submission loader's nine reads share 120 per minute (`rate-limit.ts` ignores the session). Key the default group by session for signed-in callers with the address as a ceiling, then drop the loader reads that never change within a visit. This is the one defect a real user meets on ordinary use.
2. **Done in M12a sprint 5.** **Correctness small ones (a few days).** The reminder that is lost when the job misses its exact day (`kpi.ingestion`), the comma in an organisation abbreviation that makes a provider unreachable in the v1 filter (`registry.services`), the member who cannot make a working write token on the profile page (`core.authz`/profile), and the random-port flake of `cli.test.ts` (an unchecked `20000 + random`). Each is size S.
3. **Done in M12a sprint 5, without a lockout (the maintainer's decision).** **Audit trail of sign-ins (M, with the account-lockout decision).** Login, logout and failed sign-ins are not recorded; decide it together with lockout (question below).
4. **The facet redesign (sprint 3 of M12a)** is already planned; the 360 px header and the one-item breadcrumb on the public catalogue are cheap to take with it.
5. **Then the "annoying" lines by module**, starting where several lines share a file: `registry.services` (lists cut at 100, stage sort by term key, the four calls of the service page, no draft or conflict check in the edit form), `core.audit` (offset paging, reads are not audited), and the three places where server texts are English (`core.settings`, `core-authz`, API problem texts).
6. **Leave the "nice to have" lines** for the plan that needs them; the 76 "record" lines are history and could move to the ADRs they belong to.
