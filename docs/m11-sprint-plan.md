# M11 Sprint Plan: `kpi.analytics` and the widget grid dashboard

Status: **accepted**, 2026-10-20. The maintainer answered four questions while this was drafted (recorded in §14, decisions 1 to 4) and answered "yes" to every decision marked "taken by this plan" (decisions 6 to 14) on 2026-10-20, before sprint 1 started; they stay reversible without a migration.
Scope source: [implementation.md](implementation.md) §5, M11, [architecture.md](architecture.md) (the `kpi.analytics` rows of the module, registry and job tables, and the `core.ui-shell` row, which already says "dashboard grid"), FEATURES §3.8 (the KPI analytics dashboard) and defect 10 ([FEATURES.md](FEATURES.md) §5), and what M9 and M10 hand over (the effective KPI set, the KPI history, the value types, the measurements, the chart adapter, the `ui.widget` registry).

M11 is size L in `implementation.md`. Because the maintainer added a **widget-based grid dashboard** on [Snapgrid](https://snapgrid.dev/svelte/docs/getting-started/) with a daisyUI [FAB](https://daisyui.com/components/fab/) menu and a per-user stored configuration, and PDF export leaves the milestone (decision 4), this plan has **six sprints (about seven to eight weeks for one developer)**. It adds **two runtime dependencies** (Snapgrid and dnd-kit, with their own packages) and changes one contract (`ui.widget`). It releases as `0.13.0` (`0.12.0` is M10, released 2026-10-20). M12 (`kpi.impact`) follows; Gate 3 follows M13.

3. **Facts about Snapgrid, read before drafting** (all to be re-checked by the prototype in sprint 1):

## 2. Cross-sprint rules

- **One pull request per sprint** (CLAUDE.md). ADRs, READMEs, backlog lines, the regenerated OpenAPI document and review fixes go into the sprint's pull request; push when the sprint is complete and verified (`pnpm check`, the tests of every package touched, `pnpm test:contract`, the e2e of any journey changed, `pnpm openapi:diff`).
- **Two modules change, one is new.** `core.ui-shell` owns the grid, the stored document and the FAB menu (the dashboard is a feature of the shell, decision 2); `kpi.analytics` (`modules/kpi-analytics`, package `@scorpion/kpi-analytics`) owns the calculations, the analytics reads, the exporters and the widgets that use them; `kpi.ingestion` gains one additive trusted read. `kpi.analytics` depends on `core.authz`, `core.settings`, `kpi.framework` and `kpi.ingestion`, and has `core.ui-shell` as an **optional peer**. It reads services only through `registry.services/public`. Nothing depends on it before M12.
- **The stored document is ours and is never trusted.** The dashboard is one JSON document per user in the preference `core.ui-shell.dashboard` (decision 1). A pure `parseDashboard(raw, context)` turns whatever is stored into a valid dashboard and a list of what it dropped, and never throws (a property test): an unknown widget (its module left the profile), a widget the person may no longer see, a bad configuration, an overlap, a size outside the widget's limits, a duplicate id and a too-large document are each repaired or dropped, never rendered. `GET /ui/dashboard` is the **only** reader the page uses; the generic `PUT /preferences/{key}` can still store a value (it passes the structural schema) and the reader sanitises it.
- **Widgets are registry contributions** (CLAUDE.md rule 7). A widget is an entry of `ui.widget` with the new optional grid metadata; there is no `if (widget === 'trends')` in the shell, and the FAB menu is built from the entries the caller may see. A widget is a Svelte component in its module's `ui` entry; the shell knows no widget by name.
- **The dashboard is for people who are signed in.** A visitor sees the hero and nothing else. A widget draws nothing that the caller's permission would not give, and the server leaves it out of the list before the page sees it.
- **Layouts are stored for one desktop grid (12 columns); narrow screens stack.** Below the `md` breakpoint the tiles stack in reading order (`y`, then `x`), full width, with no dragging. Per-breakpoint layouts are not stored (taken by this plan, §14).
- **Calls are counted and shared.** The page's loader reads the document and the widget list on the server, so the browser sends nothing for them on arrival. Each widget loads its data in the browser, but the widgets share **one in-flight read per distinct (service, range)** through a small client store, so a dashboard of eight widgets over two services makes two reads, not eight. The e2e spec counts what the browser sends on arrival, on adding a widget, on moving or resizing (none, until the save), and on a change of a widget's setting, writes the counts into the report and the test log (`[dashboard-calls]`), and asserts them.
- **Saving is one `PUT` after the person stops** (about one second after the last change, and when the page is left). Two tabs: the last save wins (the document has a `version` of its schema and no revision; taken by this plan).
- **Values are typed; text is not parsed.** A numeric value type gives numbers; a text value is shown as text and is never turned into a number (the legacy "first number in the string" is dropped: backlog). `HH-MM-SS` is already seconds through the value type. A gap is a gap (`null`), never zero.
- **Vocabularies and settings are data.** The thematic filter reads the vocabulary `thematic-category` everywhere (the dashboard and the defaults dialog use one list: defect 10); the thresholds of the volatility bars are module settings with defaults (0.4 and 0.8), not literals; no hard-coded branding in an export's header.
- **Accessibility is a deliverable, not a check at the end.** Every tile has a heading and an accessible name; every chart has the table of its numbers; moving and resizing have button alternatives with announcements (`role="status"`); focus is never lost when a tile moves or is removed; axe in both themes in view and in edit mode; the FAB is operable by keyboard and by touch.
- **Public v1 is unchanged** (`pnpm openapi:diff`). The new routes are internal. Update each module README with every manifest change. A new **runtime** dependency is named in the pull request and in ADR-0042 with its reason (decision 3); no other new dependency.
- Every pull request carries a changeset (package `scorpion`); sprints 1 to 6 are `minor` where an operator or a person can see something, `patch` otherwise.

## 3. The model

**No new table.** `kpi.analytics` has no tables (no `kpia_` prefix is needed until M12 or a later feature asks for one); the architecture's `dashboard_preference` is replaced by two preference keys.

**The dashboard document** (key `core.ui-shell.dashboard`, schema in `core.ui-shell`, at most 8 KiB as JSON, which the preference service enforces):

```ts
{
  version: 1,
  items: [                       // at most 20
    {
      id: 'k3x9a2',              // an instance id: 4 to 12 lower-case letters and digits, unique in the document
      widget: 'kpi.analytics.trends',   // the id of a `ui.widget` entry
      x: 0, y: 0, w: 6, h: 4,    // grid units on 12 columns; 0 <= x, x + w <= 12; 1 <= w, h
      config: { service: '…', range: '1y', category: 'Usage', cumulative: false, hidden: [], secondary: [] }  // at most 400 bytes as JSON, shaped by the widget
    }
  ]
}
```

`parseDashboard(raw, { entries, may })` returns `{ items, dropped: { id, reason }[], reset: boolean }`: the entries are the `ui.widget` registry, `may` says whether the caller holds an entry's permission; each widget's optional `configSchema` (a Zod schema in the registry entry, the way registry entries elsewhere carry schemas) validates and defaults the `config`, and a config that fails is replaced by the widget's defaults (the widget stays); sizes are clamped to the entry's `minW`, `maxW`, `minH` and `maxH`; an item that overlaps or leaves the grid is moved down by a vertical packer; a `singleton` widget appears once; more than 20 items or a document the schema refuses is replaced by the **default dashboard** (`reset: true`, and the page says so). `serialiseDashboard(items)` is the inverse, drops the keys it does not know and fails (a `RangeError`) rather than write a document over 8 KiB. `migrate(version)` is a table from each old version to the next; version 1 has none yet, and a test proves an unknown newer version is refused, not guessed.

**The default dashboard** is built from the `ui.widget` entries that carry a `default` placement (`{ x, y, w, h }`) and that the caller may see, in `order`: the three cards of today, then the KPI cards, the trends chart and the quick actions. A person with no stored document gets it; "Reset to default" in the FAB menu stores nothing and shows it again until the next change (taken by this plan).

**The extended `ui.widget` entry** (additive; every existing entry stays valid): `grid?: { w, h, minW?, minH?, maxW?, maxH?, default?: { x, y, w, h }, singleton?: boolean }`, `label?` and `description?` (keys of the module's message catalogue, shown in the FAB menu and the widget list), `icon?` (the closed icon table), `configSchema?` (a Zod schema). An entry without `grid` is a card of the old kind: it keeps the slot behaviour and is also placeable with the default size `w: 4, h: 3` (so the three existing cards need no change but their entry). The browser half receives props: `{ instance: string, config: unknown, editing: boolean, setConfig(next): void, size: { w, h } }`. A widget that ignores them (the old cards) works unchanged.

**The preference `kpi.analytics.defaults`** (registered by `kpi.analytics`): `{ service?: string, range: '3m' | '6m' | '1y' | '2y' | 'all', category: <a key of thematic-category> | 'all' }`. It seeds the configuration of a **new** widget; it is the "User dashboard defaults" of FEATURES §3.8. With no default service, a new widget takes **the first service of the person's providers by name, else none** and shows "Choose a service" (the legacy page took an arbitrary first service: a ⚠ of FEATURES §3.8).

**Ranges.** `3m`, `6m`, `1y`, `2y` and `all`, counted back from the **latest month with a value** of the service, or from the current month by the injected clock (decision: from the current month, so the window is the same for every KPI of a service and for every widget; taken by this plan). A range is **always applied**: `all` is a value, and a stored document with no range is repaired to the default `1y`, which is the fix of defect 10 (no duration meant no date filter). The months of a window are an explicit list, so a KPI with a gap shows a gap.

**The calculation library** (pure, in `modules/kpi-analytics/service/calc/`, table-driven and `fast-check` tests; registries `analytics.aggregate` and `analytics.score` carry the entries): change % from the oldest to the newest value of a window (undefined, shown "n/a", when the oldest is 0 or fewer than two values exist); `sum`, `avg`, `min`, `max` (the entries of the vocabulary `aggregate` map to these; no list of terms in the module beyond the four functions); cumulative series; **MAPE as the legacy page meant it, a mean absolute percentage deviation from the mean** (undefined when the mean is 0 or fewer than two values exist), with the two thresholds from settings; month-end handling; the seconds of a duration. Every function takes numbers and returns numbers or `null`, never throws, and never turns a gap into a zero.

**The chart spec** gains, additively, what the trends chart needs: a `secondary` flag per series (a second y axis), and the cumulative and hidden states are the widget's, not the adapter's. The adapter stays the only code that knows ECharts.

**Exporters** (registry `analytics.exporter`, entries `{ id, labels, extension, mediaType, write(table) }`): **CSV** and **XLSX** (decision 4), one row per KPI with **one column per month of the union of the series' months** (the legacy export assumed every KPI shared the first KPI's dates), the service's abbreviation in the file name, every cell escaped with `escapeCell` of `kpi.ingestion` (the CSV is UTF-8 with a BOM, as the import templates are), and no instance name or contact in the file unless the settings carry it. PDF is in the backlog (decision 4).

**Amended in sprint 1 (what was decided while building it; the reasons, the prototype's numbers and the verdict are in [ADR-0042](adr/0042-dashboard-document-and-grid.md)):**

Checked against the source before starting: `dev` carries `0.12.0` (PR #118 merged); the plan was only in the working tree and was committed with this sprint's pull request; `core.ui-shell` already depends on
`core.settings` (and `core.authz`, `contracts`, `kernel`); the preference registry and its 8 KiB cap are as described; `apps/web` has Svelte 5.57.2, SvelteKit 3.1.0 and daisyUI 5.7.50. Where the plan and the
source differed, the source won:

1. **`core.settings` had no public way to write a preference as the actor** (only the trusted read `getUserPreference`). The maintainer chose to add **`setUserPreference(actor, key, value)`** to its public service,
   which delegates to `preferences.set` (same permission, schema, cap and event). Consequence: a save also needs `core.settings.preference.write`; a read does not need the read permission. Item 4's "do not change `core.settings`" is therefore
   one additive method, with its test and README line.
2. **Snapgrid passes the prototype gate, wrapped.** No check failed. The turnkey `<GridLayout>` fails axe in edit mode, has no keyboard resize and ignores `prefers-reduced-motion`; the headless API with a move grip, a named 24 px resize handle, a remount on a mode
   change and a reduced-motion switch is clean in both themes in view and edit mode (ADR-0042, Decision 2). The grid chunk is 133.7 kB raw / 43.9 kB gzip, dynamically imported. `@snapgridjs/core` depends on `react-grid-layout` (React peers, not bundled): 19 packages are new to the lockfile, and
   `autoInstallPeers: false` makes `pnpm install` warn about unmet `react` and `react-dom`: a decision for sprint 2 (ADR-0042, Decision 4).
3. **Only `dashboard`-slot entries are tiles.** The plan says an entry without `grid` is placeable at 4×3; a `header` widget (the inbox bell) is not a card. The three cards (`registry.organisations`, `core.identity`, `core.notifications`) have no `grid` yet, so they are placeable but **not in the default dashboard**
   until sprint 2 gives them `grid.default`.
4. **"A singleton with two defaults" is not representable**: `default` is one placement; a list is refused by the strict schema, and a test says so. A repeated singleton is dropped on read and a 422 on save.
5. **The structural schema is looser than a valid dashboard** (finite numbers, at most 100 items, bounded strings) so the generic preference route can store what the reader must repair; `GET /ui/dashboard` is the only reader. A version above 1 is `reset: true` with `resetReason: 'newer-version'`; the
   instance id of a tile with no usable id is named `#<position>` in `dropped`; `isDefault` says nothing is stored; if a repaired document is still over 8 KiB the last tiles are dropped (`document-too-large`).
6. **The default dashboard is ordered by row and column**, with `order` then id deciding who keeps a place two defaults want; its instance ids are a hash of the widget id (the default is stored nowhere).
7. **The 8 KiB cap holds 20 tiles of the sizes the plan names, not 20 at the 400-byte maximum.** Measured: 20 trends tiles with the plan's example configuration are 4,257 bytes (the plan expected about 6 KiB); 20 KPI cards 2,913; 20 old cards 2,155; 20 tiles at a 325-byte configuration are 8,197 (over); 17 at 391 bytes fit.
   A document that does not fit is a 422 on `items`. Whether `MAX_CONFIG_BYTES` goes from 400 to about 300 is for the maintainer before sprint 2 (a constant, no migration).
8. **`fast-check` (4.10.2, already in the lockfile) is now a development dependency of `core.ui-shell`**; no other `package.json` changed and no runtime dependency was added.
