# M12a Plan: polish and backlog (between M12 and M13)

Status: **decisions answered on 2026-11-06 (§3); ready for approval.** Nothing here is built. The release version is decided after the scope is (a `minor` if anything is visible, so most likely `0.16.0`; M13 then follows).
Why a milestone of its own: eight small, unrelated fixes asked for on 2026-11-06 plus a slice of `docs/backlog.md` (397 open lines). It adds **no module**, no runtime dependency (`drizzle-kit` is already a dev dependency) and no public v1 change unless §2 item 3 says so (sprint 4 adds a stylesheet route on the internal surface and settings, no new module). Size S to M: **four sprints**, one pull request each (CLAUDE.md: batch).

## 2. Scope

**Sprint 1: the eight fixes** (`feature/m12a-polish`)

1. **Drizzle studio.** `drizzle.config.ts` at the root (all module schemas, `DATABASE_URL`), `pnpm db:studio`. Dev only: bound to `127.0.0.1`, never in a profile or an image, documented in CONTRIBUTING with the warning that studio can write to the database. A drift test: the config lists every module that has a `db/schema.ts`.
2. **Hierarchical token permissions.** A tree built from the dotted ids (`registry` > `services` > `service` > `read`); a parent is a tri-state checkbox (checked, partly, unchecked) that selects or clears every leaf below it and says how many it covers; keyboard (arrows, space) and axe; the stored value stays the flat list of ids, so the API is unchanged. Tree-building and selection are pure and unit-tested.
3. **`/catalog/*`** (decisions A and B). The public pages become `/catalog/services/:slug` and `/catalog/organisations/:id`; the new landing page `/catalog/services` is a **public, searchable, paged list of published services** (name search, stage and consortium facets; a new public list route on the internal surface, rate-limited, never v1). The public records move with them (`GET /catalog/services/{ref}`, `/schema-org`, `/catalog/organisations/{id}`, `/catalog/kpi/rimo.ttl` and `.jsonld`). **No redirects from `/public/...`** (the pages were never shown to users). Schema.org `url`, `PUBLIC_PAGES`, the docs, the contract and e2e tests and the ASVS V8 note follow; a test keeps "an unpublished service is the same 404 at the new address". `/services` stays the signed-in catalogue. Public v1 stays unchanged (`pnpm openapi:diff`).
4. **Facets full width** now (layout only); the redesign is sprint 3.
5. **Sidebar: the most specific entry wins**, and the **sidebar shows the hierarchy**: an entry whose path lies below another entry's path is drawn indented under it (`Pending approvals` under `Users`, `Impact` under `Services`), so the order is no longer a flat list of lookalikes. The nesting is derived from the registered `ui.nav` paths (no new field), and a unit test runs over the navigation of the `full` profile: on every page exactly one entry is current. E2E for `/admin/users/pending` and `/services/evaluate`.
6. **Token copy dialog.** The created-token view has a very large token container; reproduce it in a browser first (probably an alignment or overflow rule), fix it, and check it at narrow and wide widths and with the long and the short token.
7. **Default logos and the footer.** The Scorpion mark ships as built-in light and dark assets of the web app (**supplied by the maintainer**; sanitised like any SVG) and is the fallback of the two logo slots until an operator uploads one. The footer keeps `© year instanceName` (the maintainer's decision of 2026-11-06, after the discussion of a separate holder setting) and **adds a fixed software attribution next to it**: "Powered by Scorpion" with the version and a link to the licence. No new setting. **CLAUDE.md rule 9 ("no hard-coded branding: product name ... from settings") gets an ADR and an amendment:** the attribution of the software is the software's own identity, not instance branding; instance name, sender, URLs, contact and legal texts stay settings. A test pins the footer (the instance name in the copyright, the attribution present and not editable).
8. **Icons from Tabler, at build time** (decision on icons). `@tabler/icons` is added as a **dev dependency only**; a script (`pnpm icons:generate`) copies the icons the app uses into `packages/contracts/src/icons.ts` (the table stays closed; MIT notice added to the licence file), and `pnpm check` fails if the generated file differs. This replaces the hand-drawn paths, fixes the `cog` that is a sun, and makes every settings button a gear.

**Sprint 2: backlog** (`feature/m12a-backlog`)

- **The two pointer-drag e2e flakes** (`dashboard.spec.ts:223`, `components/dashboard-grid.spec.ts:176`): a trace of a failing run, the cause (the finding is in the backlog under "`kpi.impact` follow-ups (M12 sprint 4)"), a fix without weakening an assertion, a loop of repeats to show it holds.
- **A triage of the 397 open backlog lines**: one table (`docs/backlog-triage.md`) with each line sorted as "breaks something", "annoying" or "nice to have", with the module and a size; **no code in this step**. The maintainer picks from it; the picks are a plan of their own.

**Sprint 3: the faceted search redesign** (`feature/m12a-facets`)

The behaviour of today's faceted search (checkbox logic, counts, the URL state) is liked and stays; the look is old-school. The sprint **starts with an interactive brainstorm with the maintainer** (the directions considered: filter chips with a side drawer, a horizontal filter bar with popovers, a refreshed sidebar), then builds the chosen one or two alternatives behind a switch for comparison, applies it to both catalogues (`/services` and `/catalog/services`), keeps the keyboard and axe results, and removes the loser. The e2e journeys of the catalogue (j08) are updated, not weakened.

**Sprint 4: admin-editable theme colours** (`feature/m12a-theme-colours`; added 2026-11-06, decision: **full control**, not only a primary and an accent colour)

An administrator changes the colours of both themes (light and dark) in the Branding screen of the admin area. Size: about one sprint (the estimate given was 2 to 3 days for the full set).

1. **Settings.** A `colors` group in the branding settings of `core.settings`, one value per daisyUI colour token for each of the two themes (`primary`, `secondary`, `accent`, `neutral`, `base-100`, `base-200`, `base-300`, `info`, `success`, `warning`, `error`, and the `*-content` pairs), each optional; an unset token keeps the built-in value. The values are `#rrggbb` only, never free CSS. The screen is generated from the schema like the rest of the branding screen; a "reset to default" per theme and a preview of the two themes.
2. **Delivery under the CSP.** The policy allows no inline style, so the overrides are a **stylesheet route** (for example `GET /theme.css` on the web app, built from the branding read) linked from the layout, with a version in its address so a change is seen at once and a short cache. It writes only the variables of the known tokens, with values that passed validation, nothing else. The built-in themes stay in `app.css`; the route only overrides.
3. **Contrast.** A pure function checks every text/background pair of the tokens (content on its colour, base-content on the three base colours) against WCAG AA (4.5:1; 3:1 for large text and borders) for each theme; a failing set is refused on save with the pair named, and the content colours may be left to be derived (the best of black and white). Table-driven unit tests, a rollback test (nothing is half-saved), a denied-permission test.
4. **Everything that draws colour follows the tokens.** The charts (palette), the badges, the sparkline and the logos' theme switch read the variables, not fixed colours; a test fails for a hard-coded colour in `modules/**/ui` and `packages/ui-kit` outside the palette definition. The e2e suite runs axe in both themes with a custom set applied, under both base paths.
5. **Docs.** README of `core.settings` and `core.ui-shell`, an ADR for the stylesheet route (a decision about the CSP and the cache), the docs export, and an ASVS note if a scoped path changes. The documentation screenshots keep the default colours (the custom set is applied only inside the tests).

## 3. Decisions (answered 2026-11-06)

- **A. Landing page:** a public searchable list of published services (item 3).
- **B. API paths:** all public records move under `/catalog`, without redirects (item 3).
- **C. Backlog:** the two drag flakes and a triage table (sprint 2). The logo artwork is supplied by the maintainer.
- **Icons:** generated from Tabler at build time, a dev dependency only (item 8).
- **Copyright:** the footer keeps `© year instanceName` and gains the fixed "Powered by Scorpion" attribution; no `copyrightHolder` setting (the maintainer's final decision; rule 9 is amended by an ADR for the attribution, item 7).
- **Redesign:** its own sprint, decided in a brainstorm at its start.
- **Theme colours:** a sprint of its own (sprint 4), with **full control** of the colour tokens of both themes, not only a primary and an accent colour (the maintainer's decision, 2026-11-06).

## 4. Rules for the milestone

Every change keeps the module rules and the security rules of CLAUDE.md; `docs/security/**`-scoped paths get their ASVS notes (item 3 touches public pages: V8 note and a test that an unpublished service is still a 404 at the new address); one changeset per pull request; READMEs follow manifest changes; the e2e specs run under both base paths.

## 5. Found differently / Amended in sprint 1

Checked against the source while building sprint 1 (2026-11-06):

- **Item 1.** Studio needs `drizzle-kit studio --host 127.0.0.1`; `pnpm db:studio` wraps it (`scripts/db-studio.ts`, reads `.env`, refuses `NODE_ENV=production`). The kernel's `packages/kernel/src/db/schema.ts` is listed too, not only the modules.
- **Item 3.** No Schema.org `url` or `@id` ever named `/public/`: they name the signed-in pages (`/services/{id}`, `/organisations/{id}`), so nothing there changed (ADR-0049; backlog: should a public profile identify itself by the public page?). `/public/kpi/rimo.*` moved too (ADR-0040 names it). The list returns its facets in the same answer (a second route `/catalog/services/facets` would shadow a service whose slug is `facets`), and the facet values are named `options` because the pinned-field test forbids a property called `values` in any public schema. A `sort` parameter is ignored, not refused (it is one of the shared non-filter names).
- **Item 5.** The sidebar rule also nests `Notifications` under `Profile` (`/profile/notifications`), which the plan did not name; it follows from "derived from the paths". A nested entry is drawn right after its parent, within the same section.
- **Item 6.** Reproduced: daisyUI's `.alert` is a grid with one column per child, so `flex-col` did nothing and the token sat in a 33 px column at 360 px (576 px tall). The fix is `flex flex-col items-stretch`. The token has one length; the long case is a long token name. The shell header itself is wider than a 360 px screen (backlog).
- **Item 7.** The maintainer supplied the logos as PNG with the "Powered By Scorpion" text in the image, and asked for cropped favicons. The maintainer's PNGs are in `apps/web/src/lib/assets/` (`scorpion-light.png`, `scorpion-dark.png`), scaled to 128 px high to keep the page light; `scorpion-favicon.png` is the tile of the dark logo cropped to a square at 64 px. The layout handles a `data:` address (small files) as well as a hashed asset. Showing the product version to visitors departs from ADR-0045, which keeps module versions from them (ADR-0050 says so).
- **Item 8.** `Bell.svelte` had its own copy of the bell path; it uses `Icon` now. Tabler is stroke width 2, so both `Icon` components moved from 1.75 to 2. `dot` is Tabler's `point`. The licence notice lives in `THIRD_PARTY_NOTICES.md` (the repo kept none; `LICENSE` stays plain ISC so licence detection is not disturbed).
